# 回滚演练脚本

> 目的：在真实切换前证明"出问题时能退回去"，并把回滚变成可执行、可验证、可审计的动作，
> 而不是上线当晚的临场发挥。

## 1. 回滚层级

| 层级 | 场景 | 手段 | 影响面 |
|---|---|---|---|
| L1 应用回滚 | 新版本功能异常、错误率升高 | `platform-release` 记录 ROLLBACK，部署上一成功版本 | 单组件/单服务 |
| L2 迁移批次回滚 | 某批历史数据错误 | `platform-migration` 按批次回滚（依赖逆序、链式） | 单目标/多目标 |
| L3 配置/字典回滚 | 字典或映射错误 | 主数据变更申请回退 / 映射停用 / 版本链恢复 | 字典与业务引用 |
| L4 整体回退 | 多域不可用、无法在窗口内修复 | 切回老系统/只读模式，按停机预案执行 | 全院 |

## 2. 触发条件与决策

**触发条件（满足任一）**：

- P1 事件在 SLA 内无法缓解，且影响挂号/收费/医嘱/发药/报告等核心流程；
- 迁移数据出现不可接受的账实不符（金额、患者身份、医嘱-收费不一致）；
- 安全事件（数据泄露、越权访问）无法通过配置立即收敛；
- 性能崩溃导致核心业务不可用，且扩容/降级无效。

**决策**：

- 由事件指挥人提出，业务负责人与技术负责人共同确认；任一否决则不得整体回退；
- L1/L2 可由技术负责人直接决策，但必须在事件/工单中记录原因与范围；
- 决策记录写入事件轨迹（`platform-ops`），包含：时间、范围、目标版本/批次、预期影响、验证人。

## 3. 演练前准备

- [ ] 确认上一成功版本与镜像摘要（`release` 部署记录）；
- [ ] 确认迁移批次号、目标依赖顺序与回滚顺序（`migration` 批次清单）；
- [ ] 确认数据库备份可用，恢复演练已完成；
- [ ] 确认停机窗口、通知模板、业务验证人；
- [ ] 确认回滚期间冻结新变更（`release` FREEZE 窗口）；
- [ ] 确认值班与指挥人（`ops` 值班表 + 事件预案）。

## 4. 演练步骤

### D-1 预检

1. 在预发布环境部署"新版本"，完成一轮核心流程（挂号→接诊→医嘱→收费→发药→报告→病历签名）；
2. 记录基线：关键接口 P95、错误率、核心表行数、收费金额合计；
3. 记录新版本部署 ID 与迁移批次号。

### D0 执行回滚

**L1 应用回滚**

1. 在 `release` 中调用 `POST /api/v2/release/deployments/{id}/rollback`，填写原因；
2. 确认生成 ROLLBACK 记录且 `rollbackOf` 指向原部署；
3. 验证目标版本镜像摘要与上一成功版本一致；
4. 观察 5xx、P95、连接池与关键业务日志。

**L2 迁移批次回滚**

1. 收集需要回滚的批次号（按依赖逆序：费用明细→收费/医嘱→就诊→患者→字典）；
2. 调用 `POST /api/v2/migration/batches/rollback`，一次提交多个批次；
3. 预期行为：
   - 目标行在应用后被人修改 → 整批拒绝（409），列出差异字段；
   - 链式回滚（UPDATE 后再回滚 CREATE）→ 内容恢复/删除均成功；
4. 回滚后查询对账接口，确认表行数与金额回到基线。

**L3 配置/字典回滚**

1. 通过主数据变更申请回退条目/映射；禁止直接改库；
2. 验证业务引用已刷新（缓存/订阅）；
3. 记录回退前后的版本号与审计记录。

### D+ 验证

- [ ] 核心流程全部可走通（挂号/收费/医嘱/发药/报告/病历/医保）；
- [ ] 关键接口错误率、P95 回到基线；
- [ ] 迁移目标表行数/金额与基线一致；
- [ ] 无新增 P1/P2 事件；
- [ ] 业务关键用户签字确认；
- [ ] 回滚记录、批次号、审计记录归档。

## 5. 回滚失败兜底

- 若 L1 失败：检查镜像/配置/数据库连接，必要时切到上一副本组；
- 若 L2 失败：停止后续批次，保留现场，按差异字段人工核对；禁止"强行删除"；
- 若 L4 整体回退：按停机预案切回老系统，冻结新系统写入，保留双向对账窗口；
- 所有兜底动作必须记录在事件轨迹，并在复盘中分析根因。

> 预计影响：____；指挥人：____；业务验证人：____。

**回滚完成**

> 【回滚完成】时间：____；结果：成功/失败；当前版本/批次：____；
> 业务验证：通过/未通过；遗留问题：____；下一步：____。

## 7. 复盘要求

- 事件复盘必须在 `platform-ops` 中创建并走完 DRAFT → REVIEWED → APPROVED；
- 必须回答：触发原因、发现时延、决策时延、回滚耗时、数据影响、是否有更早的预警信号；
- 纠正措施至少包含：监控/告警改进、发布检查单改进、迁移校验改进、培训改进；
- 纠正措施进入下一发布列车，并在下一次演练中验证。
