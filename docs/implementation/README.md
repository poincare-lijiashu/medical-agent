# 实施方法论

> 适用范围：本仓库交付的全院级平台（Java 业务微服务 + Python AI 中台）在院内的实施、迁移、
> 培训、上线与稳定运行。本文是实施团队的作业标准，不是产品介绍。

## 1. 目标与原则

实施的目标不是"把软件装上去"，而是让医院在**可控风险**下完成业务切换，并且在切换后
能够独立运行、独立排障、独立迭代。四条原则：

1. **先治理、后迁移**：字典/科室/收费项目/诊断先进入主数据治理（§269），再迁移业务历史（§270）；
2. **先演练、后切换**：迁移回滚、应用回滚、值班与工单必须在上线前完成演练（§271/§272/§273）；
3. **先证据、后签字**：每个门禁的通过条件都是可核验的证据（报告、截图、批次号、工单号、审计记录），
   不接受"口头确认"；
4. **业务签字、技术兜底**：业务负责人对流程与数据负责，技术负责人对系统与回滚负责，
   任何一方都有否决权（见 Go/No-Go 规则）。

## 2. 五阶段与门禁

| 阶段 | 目标 | 关键动作 | 出口门禁（必须全部满足） |
|---|---|---|---|
| S1 准备 | 明确范围、组织与基线 | 项目章程、范围清单、RACI、环境与账号、风险台账 | 范围与验收标准签字；环境可登录；数据源清单确认 |
| S2 蓝图 | 把"院内流程"映射到系统能力 | 业务流程蓝图、角色权限矩阵、接口清单、报表清单、差异清单 | 蓝图评审通过；差异有明确"改系统/改流程/不上线"结论 |
| S3 构建与配置 | 字典、权限、接口、报表、AI 知识库就绪 | 主数据域注册与同步、角色与数据范围、接口联调、模板配置 | 主数据质量看板无阻塞项；接口联调全部通过；权限矩阵签字 |
| S4 迁移与演练 | 历史数据搬入且可回滚 | 迁移模板与映射档案、预检、分批应用、对账、回滚演练、全流程演练 | 迁移对账通过；回滚演练通过；关键用户 UAT 签字 |
| S5 上线与稳定 | 切换、保障、交接 | Go/No-Go、切换执行、值守、问题闭环、运维交接、复盘 | Go 决议签字；上线后问题清单关闭；运维交接签字 |

> 门禁不是"文档检查"，每一项都必须指向平台里的真实记录：
> 主数据质量看板、迁移批次号与对账报告、工单号、事件复盘、发布列车号、部署记录。

## 3. 角色与职责（RACI）

R=负责执行，A=最终负责，C=需咨询，I=需知会。

| 活动 | 业务负责人 | 实施经理 | 技术负责人 | 数据治理员 | 运维/值班 | 安全合规 |
|---|---|---|---|---|---|---|
| 范围与验收标准 | A | R | C | C | I | C |
| 业务流程蓝图 | A | R | C | C | I | I |
| 主数据治理 | C | R | C | A | I | I |
| 历史数据迁移 | C | R | C | A | I | I |
| 权限与数据范围 | A | R | C | C | I | C |
| 接口联调 | I | R | A | I | C | I |
| 性能与容量 | I | C | A | I | R | I |
| 安全与等保证据 | I | C | C | I | C | A |
| 培训与认证 | A | R | C | C | I | I |
| 上线 Go/No-Go | A | R | A | C | C | C |
| 回滚决策 | A | C | R | C | R | I |
| 上线后复盘 | A | R | C | C | R | I |

> 同一个人可以承担多个角色，但**提交与审批、部署与审批、迁移与回滚**必须分离（平台已强制）。

## 4. 各阶段作业要点

### S1 准备

- 确认上线范围：哪些院区、哪些科室、哪些业务域（门诊/住院/药房/医技/病历/医保/物资）；
- 建立环境：生产、预发布、培训、迁移演练四套环境，账号与密钥由安全合规归口；
- 建立风险台账：数据质量、接口对端、网络、老系统停机窗口、关键用户可用性；
- 明确"不做什么"：本期不上线的科室/流程必须写入范围清单，避免上线前临时加戏。

### S2 蓝图

- 用**角色 × 场景**描述流程，而不是按菜单罗列功能；
- 每个差异必须给出结论：改系统（进入发布列车）/ 改流程（业务签字）/ 暂不上线（记录风险）；
- 权限矩阵必须落到权限点（`clinical:*`、`empi:*`、`mdm:*`、`ops:*`、`release:*`），
  不接受"给个管理员就行"；
- 接口清单必须包含对端系统、协议、方向、频率、失败重试与责任人。

### S3 构建与配置

- 字典先治理：科室/收费/诊断/药品/检查检验/耗材/班次/组织/院区进入 MDM，跑质量看板；
- 外部编码映射必须先建再联调，禁止"上线后手工补编码"；
- 角色与数据范围按最小权限配置，管理员账号数量受控并登记；
- 报表与打印模板由业务确认样例，避免上线当天才发现格式不对。

### S4 迁移与演练

- 迁移顺序固定：字典 → 患者主索引/跨系统标识 → 就诊 → 住院 → 诊断 → 医嘱 → 收费单 → 费用明细；
- 每批必须先预检、再应用；预检有 ERROR/CONFLICT 不允许应用；
- 每批应用后做对账（行数/金额/关键字段），对账报告归档；
- 回滚演练必须覆盖：单批回滚、多批链式回滚、应用后人工修改导致回滚被拒绝的场景；
- 全流程演练至少覆盖：挂号 → 接诊 → 医嘱 → 收费 → 发药 → 报告 → 病历签名 → 医保结算清单。

### S5 上线与稳定

- Go/No-Go 按 `go-live-checklist.md` 逐项核验，任何"阻塞项"未关闭即 No-Go；
- 切换窗口内冻结非必要变更（在平台 `release` 服务登记 FREEZE 窗口）；
- 上线后问题统一走工单（`platform-ops`），严重问题升级为事件并指定指挥人；
- 稳定期结束前完成运维交接：账号、密钥、监控、备份、告警、值班表、应急预案；
- 复盘必须产出纠正措施与责任人，并进入下一发布列车。

## 6. 风险与变更控制

- 所有范围变更走变更单：影响评估（范围/数据/接口/培训/回滚）→ 业务与技术双签 → 进入发布列车；
- 上线前冻结窗口内只允许**已审批补丁**的 HOTFIX（平台 `release` 服务强制）；
- 数据迁移脚本不允许"临时改一行"：任何映射变更必须更新映射档案并重新预检；
- 风险台账每周更新，红/黄/绿三色，红色风险必须有责任人与缓解措施。

## 7. 与平台模块的对应关系

| 方法论活动 | 平台能力 |

| 字典治理与映射 | `platform-masterdata`（域、版本链、审批、质量看板） |
| 历史数据迁移 | `platform-migration`（模板、映射、预检、应用、对账、回滚） |
| 上线后问题处理 | `platform-ops`（SLA、工单、值班、事件、复盘） |
| 版本与补丁 | `platform-release`（版本、列车、兼容、补丁、冻结、部署回滚） |
| 安全与审计 | 各服务审计表 + 统一审计查询；等保证据包见 `docs/` 相关批次 |
