# 国内医院信息化与医保对接调研（MedAssist 落地视角）

> 目的：把"医院里到底有哪些系统、网络怎么分区、医保是不是专线、接口怎么对"讲清楚，
> 并落成 MedAssist 的**可执行对接设计与交付边界**。
>
> 口径：本文区分三类信息——
> - **事实**：来自国家/省级医保局公开规范、行业标准文本（可核验）；
> - **通行做法**：行业普遍工程实践（不同院区有差异，不作为强制结论）；
> - **待确认**：必须由目标医院信息科/医保办/厂商现场确认后才能编码的项。
>
> 结论先行：**医院外网极少、医保是专网 + 前置机、院内集成以集成平台/视图库为枢纽**。
> 因此 MedAssist 的默认形态必须是"院内私有化部署 + 全部依赖内网可解析 + 不依赖任何公网服务"，
> 对接走"适配器 + 集成平台"而不是直连各业务库。

---

## 一、医院信息化的分层结构（通行做法）

### 1.1 业务系统分层

| 层 | 典型系统 | 说明 |
|---|---|---|
| 核心临床 | HIS（挂号/收费/住院/医嘱）、EMR（电子病历）、CIS（临床信息） | HIS 常是"交易与计费主库"，EMR 是"病历文书主库"；两者可能同厂也可能不同厂 |
| 医技 | LIS（检验）、PACS/RIS（影像）、超声/内镜/病理、心电、手术麻醉 | 多为专科厂商，接口以 HL7 v2 / DICOM / WebService 为主 |
| 运营管理 | HRP（人力/财务/物资）、OA、绩效、病案、医保结算 | 与临床弱耦合，但医保结算与之强相关 |
| 平台层 | 集成平台（ESB/消息中间件）、CDR 临床数据中心、视图库、主数据/患者主索引 EMPI | **对接的真正枢纽**；新系统原则上不与业务库直连 |
| 区域/上级 | 医保信息平台、全民健康信息平台、疾控/妇幼上报、检查检验互认 | 走专网或政务外网，通常经前置机/网关 |

**关键事实**：三级医院普遍已建"集成平台 + CDR/视图库 + EMPI"。新系统（含 AI 中台）
若直连 HIS/EMR 生产库，会被信息科直接否决——既影响生产库稳定性，也无法通过等保与
数据安全审查。**正确接入点只有一个：集成平台（或院方指定的视图库/服务总线）。**

### 1.2 接口技术形态（按年代并存）

1. **HL7 v2.x**（ADT/ORM/ORU）：老系统主流，管道符分隔消息；
2. **WebService（SOAP）**：2010 年代主流，各家 WSDL 不同；
3. **REST/JSON**：新建系统主流，但字段命名各院自定义；
4. **数据库视图/中间表**：仍有大量存量（只读视图最常见），性能与耦合风险高；
5. **消息队列/FHIR**：新建集成平台逐步采用，FHIR R4 在国内仍以"平台内部规范"为主。

> 结论：对接层必须"一院一适配"，不能指望统一协议。MedAssist 的 `backend/integration/`
> 端口-适配器设计（见 `docs/INTEGRATION.md`）就是为此而设。

### 1.3 合规与评测（决定"能不能上线"，不是"能不能跑通"）

| 事项 | 性质 | 对 MedAssist 的要求 |
|---|---|---|
| **网络安全等级保护 2.0**（三级为主） | 强制 | 部署在内网安全域；运维端口不对外；日志留存 ≥6 个月；账号/权限/审计三件套（本系统已具备） |
| **电子病历系统应用水平分级评价**（4~6 级） | 评级（影响采购） | 要求"全院信息共享、闭环、CDSS 可追溯"；AI 输出必须**可溯源 + 有人复核**（本系统已按此设计 HITL 门） |
| **医院智慧服务/智慧管理分级** | 评级 | 患者服务侧能力，非本期重点 |
| **互联互通标准化成熟度测评**（四级甲等及以上） | 评级 | 要求标准数据集 + 交互服务；对接输出应尽量贴合 WS/T 500 系列标准文档 |
| **数据安全法 / 个保法 / 《医疗卫生机构网络安全管理办法》** | 强制 | PHI 不出院、最小必要、加密存储、访问留痕（本系统：字段级 AES-256-GCM + 追加审计） |
| **《生成式人工智能服务管理暂行办法》** | 强制（面向公众服务） | 院内自用不面向公众，但仍需内容标识、人工复核、可追责；不得直接给出最终诊断结论 |

> 待确认：目标医院当前等保级别、是否要求通过"院内 AI 应用安全评估"、是否要求模型
> 与知识库版本受控（涉及变更审批流程）。

## 二、医院网络分区（这决定"能不能外网"）

### 2.1 典型分区

```
┌──────────────────────────────── 医院内网（生产域，等保三级）──────────────────────────────┐
│  HIS/EMR/LIS/PACS  ←→  集成平台/CDR/视图库  ←→  MedAssist（AI 中台，K8s 集群）           │
│         ↑                                                                                 │
│         │ 只读服务/消息（经集成平台，不直连生产库）                                        │
└─────────┼─────────────────────────────────────────────────────────────────────────────────┘
          │
   ┌──────▼──────┐   专线/医保 VPN    ┌──────────────────────────┐
   │ 医保前置机   │ ─────────────────→ │ 省/国家医保信息平台        │
   │（院内 DMZ）  │ ←───────────────── │（定点机构结算/目录/编码）  │
   └──────┬──────┘                    └──────────────────────────┘
          │ 双向网闸/防火墙策略（仅放行医保接口 IP:端口）
   ┌──────▼──────┐
   │ 互联网出口   │  通常仅限：官网/公众号/预约挂号/支付回调，且经 DMZ 反向代理
   └─────────────┘
```

通行做法（事实性描述）：

- **内网与互联网物理/逻辑隔离**，多数医院**不开放通用互联网访问**；
- 需要外网的业务（如药品追溯、部分上报）走**指定白名单 + 代理**，不是"给服务器开外网"；
- 运维跳板机 + 堡垒机，服务器不允许直连公网。

### 2.2 对 MedAssist 的硬约束（已在本仓库落实）

| 约束 | 落实点 |
|---|---|
| 不得在运行时访问 HuggingFace / 公网模型仓库 | `EMBED_ALLOW_DOWNLOAD=false`（默认）、`HF_HUB_OFFLINE=1`、`TRANSFORMERS_OFFLINE=1`；权重缺失**报错而不是偷偷下载**（`backend/core/embedder.py`） |
| 不得依赖 PubMed 等境外接口 | `PUBMED_ENABLED` 开关；生产默认 `false`，连 DNS 都不发（`backend/agents/medical/literature/nodes.py`） |
| LLM 必须可指向院内私有化推理 | `QWEN_BASE_URL` 指院内 vLLM/Ollama 网关；`LLM_PRIVATE_HOSTS_ALLOWLIST` 限定私网地址 |
| 镜像/依赖全部内网可拉 | `deploy/offline/`（镜像清单 + `docker save/load` + Harbor 推送 + 校验清单） |
| 启动即自检"有没有偷偷连公网" | `backend/core/offline_guard.py` 打印 `medical_agent.network_deps`，生产命中公网端点则 `warning` |
| 离线交付与开发机解耦 | `deploy/offline/README.md` §4「与开发机边界」 |

## 三、医保系统：是不是专线？怎么接？

### 3.1 结论（事实）

**是专线（或医保专用 VPN/政务外网通道），不是公网。**

- 定点医药机构接入**国家医保信息平台**，按国家医保局要求通过**专线方式**接入；
- 院内需部署**医保前置机**（或由医保局/运营商提供的前置网关），业务系统**不直接**访问省/国家平台；
- 接口基于**全国统一的医保接口规范**（俗称"医保接口 V1.0"，各省在其上做本地扩展）；
- 报文安全：**SM2 签名 + SM4 加密**（国密），HTTP(S) 承载，报文为 JSON/XML（各省有差异）；
- 交易以**交易编号（`infno`，4 位）**区分（如人员信息、门诊结算、住院结算、目录下载、结算清单上传等）；
- 报文流水号 `msgid` 通行规则为 **定点机构编码(12) + 时间(14, yyyyMMddHHmmss) + 顺序号(4)**；
- 另有"**接口接入**"与"**网页版接入**"两种模式（小型机构可用网页版，二级以上医院基本走接口）。

> 待确认（必须现场拿到的资料）：
> 1. 本省医保局下发的**接口规范版本号与本地扩展说明**（含 `infno` 全集与必填项）；
> 2. 前置机型号/操作系统/中间件/证书（SM2 证书、密钥介质、有效期与更新流程）；
> 3. 专线开通方（医保局 or 运营商）、IP/端口、是否需要固定源 IP 白名单；
> 4. 测试环境账号与环境地址（**没有测试环境就不要开工编码**）；
> 5. 结算清单（4101/4102 类）上传时限与重传规则。

### 3.2 医保相关业务链（医院侧要处理的）

| 环节 | 说明 | MedAssist 相关性 |
|---|---|---|
| 目录下载（药品/诊疗/耗材/疾病/手术） | 医保三大目录与院内编码映射 | **高**：AI 开方/用药审查必须用医保目录口径，否则"能开但不能报" |
| 患者参保信息查询 | 人员类别、待遇、慢特病标识 | 中：影响用药与自付提示 |
| 门诊/住院费用结算 | 上传费用明细、预结算、正式结算、退费 | 低（HIS 主责），但 AI 需读结算结果做费用提示 |
| **医保结算清单** | 按国家统一编码上传（诊断/手术/费用归类） | **高**：DRG/DIP 付费的核心凭证，AI 病案质控可直接产出建议 |
| DRG/DIP 分组 | 本地分组器或省平台返回 | 中高：AI 可做"入组风险提示/主诊断选择建议" |
| 医保码 / 移动支付 / 电子处方流转 | 医保电子凭证、处方流转中心 | 低~中：二期 |
| 智能监管/审核规则 | 违规提醒（超量、重复、限制用药） | **高**：可与本系统用药审查合并为"医保+临床"双规则 |

### 3.3 接入技术要点（写代码前必须落纸的契约）

1. **签名与加密**：SM2 私钥签名（机构侧）、SM4 会话密钥加密业务报文；密钥不得进代码库，
   走 K8s Secret/密钥管理；轮换要有停机窗口与回滚方案。
2. **重试与幂等**：医保接口以 `msgid` 去重；网络超时**必须查证后再重发**（严禁盲目重试导致重复结算）。
3. **对账**：每日结算对账（院内金额 vs 医保返回），差异进人工队列。
4. **时限**：结算清单上传有明确时限，需定时任务 + 失败告警。
5. **审计**：每一次医保交易（请求/响应摘要/耗时/结果码）必须留痕 ≥6 个月（等保要求）。

## 四、MedAssist 的落位设计（不写假 mock，先定契约）

### 4.1 三层对接边界

```
MedAssist 核心（零感知）
   │
   ├── integration/            ← 院内系统适配（HIS/EMR/集成平台/视图库）  【已有】
   │      HisAdapter: fetch_patient / fetch_orders / push_qc_result
   │
   └── insurance/              ← 医保适配（本期新增，独立包，避免与院内耦合）
          InsuranceAdapter:
            query_person(patient_id)              # 参保信息
            download_catalog(kind, version)        # 目录下载（药品/诊疗/耗材/病种/手术）
            pre_settle(visit) / settle(visit)      # 预结算/正式结算（HIS 主责时可只读）
            upload_settlement_list(list)           # 结算清单上传
            push_medical_record_qc(suggestions)    # 病案质控建议回写（可选）
```

原则：
- **只做"读 + 建议 + 回写建议"**，不做收费与结算主流程（那是 HIS 的责任边界，也是责任划分）；
- 医保适配器**不实现业务规则**，只做协议/签名/重试/对账；规则在 `core/` 内可测；
- 所有出界调用有**超时 + 熔断 + 审计**（复用现有 `literature` 的熔断范式）。

### 4.2 EMPI 与医保编码的关系

- 院内 EMPI 已有 `crosswalk(system_code, external_id)`（见 `platform/empi`）；
- 医保侧需新增两类别名：`YB_PERSON`（医保人员编号/证件号）、`YB_VISIT`（医保就诊号/结算流水）；
- **同一患者多条医保身份**（异地、职工/居民切换）用 crosswalk 多行表达，不覆盖。

### 4.3 数据模型增量（设计，不含实现）

| 表/对象 | 用途 | 关键字段 |
|---|---|---|
| `ins_catalog_item` | 医保目录缓存（药品/诊疗/耗材/病种/手术） | `kind, yb_code, name, spec, limit, version, effective_from` |
| `ins_catalog_map` | 院内编码 ↔ 医保编码 | `local_system, local_code, yb_kind, yb_code, status` |
| `ins_txn_log` | 医保交易留痕（审计/对账） | `msgid, infno, req_hash, resp_code, elapsed_ms, ts` |
| `ins_settlement_list` | 结算清单上传状态 | `visit_id, version, uploaded_at, status, err_code` |
| `drg_group_result` | 分组结果与建议 | `visit_id, group_code, weight, risk_flags` |

> 说明：以上为契约层设计，落库前须与院方确认字段口径（尤其"限制用药"与"适应症"字段），
> 否则做出来就是一张对不上账的表。

## 五、落地路线（稳中求进，每步可验收）

| 阶段 | 交付 | 验收标准 | 前置条件 |
|---|---|---|---|
| P0 环境就位 | 内网 K8s + Harbor + PG/Redis/Milvus + 私有化 LLM | 全部 Pod 镜像来自院内 Harbor；断外网后重启仍可用 | 院方给资源与网段 |
| P1 院内只读对接 | 集成平台适配器（患者/医嘱/报告只读） | 真实患者可查，字段映射经信息科签字 | 集成平台接口文档 + 只读账号 |
| P2 质控回写 | qc 结论回写（可选开关） | 回写幂等、失败不影响主流程 | 回写接口规范 |
| P3 医保只读 | 目录下载 + 参保查询 + 结算结果只读 | 目录与院内编码映射准确率 ≥99%（抽样） | 测试环境 + SM2 证书 |
| P4 医保增值 | 结算清单/病案质控建议、DRG 入组风险提示 | 建议采纳率与人工复核记录可追溯 | 病案室参与规则评审 |
| P5 扩容 | AI 中台多副本（先把文件态迁 PG/Redis） | 扩容后限流/会话/审计语义不变 | 见 `deploy/helm/.../values-prod.yaml` aiCore 注释 |

## 六、风险清单（按"会卡住项目"排序）

1. **没有测试环境就开工**：医保接口无法验证，最有杀伤力。→ 合同里写死"提供测试环境"。
2. **接口规范版本不一致**：省级扩展字段与国标不同，按记忆编码必错。→ 只认院方书面下发版本。
3. **密钥管理不当**：SM2 私钥进 Git/镜像 = 重大事故。→ Secret 注入 + 轮换演练。
4. **直连生产库**：信息科一票否决。→ 只走集成平台/视图库。
5. **AI 输出被当成诊断结论**：合规红线。→ 全部输出带"辅助建议/需医师确认"标识 + 强制复核门。
6. **离网假设被打破**：某个依赖偷偷联网，上线当天超时。→ `offline_guard` + 断网演练纳入验收。
7. **数据规模被低估**：历史病历/影像检索需求一旦放开，单机 Milvus 与单副本 AI 中台会成瓶颈。→ 先做容量模型（病历条数 × 向量维度），再定分片。

## 八、参考依据

- 国家医保局《医疗保障信息平台 便民服务相关技术规范》（2025 年发布）——移动支付/医保码/处方流转技术要求；
- 国家医保局**医保信息平台接口规范 V1.0**（各省下发本地化版本）——`infno`/`msgid`/SM2/SM4/前置机接入；
- 国家医保局《医疗保障基金结算清单填写规范》与 DRG/DIP 付费相关技术规范；
- GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》；
- 国家卫健委《电子病历系统应用水平分级评价标准》《医院智慧服务分级评估标准体系》；
- WS/T 500 系列《电子病历共享文档规范》、WS 445 系列《电子病历基本数据集》；
- 《中华人民共和国数据安全法》《个人信息保护法》《医疗卫生机构网络安全管理办法》。

> 上述规范文本以**院方/医保局正式下发件**为准；本文仅用于架构决策，不作为合规结论。
