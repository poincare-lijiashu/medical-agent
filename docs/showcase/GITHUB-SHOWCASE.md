# GitHub 展示页设计方案

> 目标：让一个陌生工程师在 **30 秒内**判断"这个仓库有深度、不是演示项目"，
> 在 **5 分钟内**愿意点进架构文档与评测报告。
> 本文件是设计稿；可直接使用的 README 成品见 [README-DRAFT.md](./README-DRAFT.md)。

---

## 1. 设计原则

| 原则 | 具体做法 | 反面案例（本方案避免） |
|---|---|---|
| 先给结论，再给细节 | 首屏 3 行说清"是什么 + 多大规模 + 最硬的三点" | 开头写 20 行愿景 |
| 用数字证明深度 | 16 服务 / 913 端点 / 334 表 / 2,140 测试，全部可从仓库复核 | 只写"高性能、高可用" |
| 用图代替形容词 | 7 张 Mermaid 架构图 + 1 张 hero SVG | 大段文字描述架构 |
| 诚实建立信任 | 单列"已知边界"，并链接到评测报告 §3 | 把待办写成"已完成" |
| 一屏一动作 | 每节结尾给一个可点击入口（架构/部署/评测） | 链接堆在文末 |

## 2. 视觉系统

| 项 | 取值 | 说明 |
|---|---|---|
| 主色 | `#1f6f5c`（深青绿） | 与产品 `tokens.css` 的 accent 一致，医疗感但不落"蓝白"俗套 |
| 强调色 | `#7fd8bf` | 仅用于 hero 渐变与关键数字 |
| 深色底 | `#0b1512 → #122b25` | hero 背景，衬托青绿 |
| 正文色 | `#1f2933` / 反色 `#eaf5f1` | 与 GitHub 亮/暗主题都能读 |
| 字体 | IBM Plex Sans + IBM Plex Mono | 与产品同源；代码块/数字用 Mono |
| 圆角 | 10–12px | 与产品卡片一致 |
| 图形语言 | 细网格 + 单侧竖线 + 少量光晕 | 表达"工程仪表盘"而非"营销海报" |

**素材规范**
- hero：`docs/showcase/assets/hero.svg`，1280×340，纯矢量、无外链字体（GitHub 可渲染）；
- 架构图：Mermaid 源码入库（可 diff、可评审），不贴 PNG；
- 截图：统一 1440×900、暗色主题、去掉浏览器边框与真实姓名（用演示数据）；
- 动图：只做 1 个 8–12 秒的"登录 → 驾驶舱 → 医嘱"链路，≤5MB。

## 3. 页面结构（从上到下）

| # | 区块 | 目的 | 内容要点 |
|---|---|---|---|
| 1 | Hero | 3 秒定性 | SVG 横幅 + 一句话定位 + 7 个静态徽章 |
| 2 | 导航行 | 降低跳转成本 | 架构 / 开放平台 / 部署 / 评测 / 上传说明 |
| 3 | 这是什么 | 消除"又一个 CRUD"误解 | 16 服务、15 schema、913 端点、完整链路 |
| 4 | 为什么值得读 | 给出 5 个可验证理由 | 每条都带"可复核证据"（迁移数、测试数、启动守卫） |
| 5 | 架构一览 | 证明有设计 | 简化 Mermaid + 链接到 7 图全量文档 |
| 6 | 能力地图 | 展示业务广度 | 12 行表格，每行"能力 + 亮点设计" |
| 7 | 快速开始 | 降低试用门槛 | 4 条命令，依赖版本明确 |
| 8 | 部署形态 | 证明可交付 | 本地 / Helm / 多院 Cell |
| 9 | 文档地图 | 证明文档体系 | 8 个入口，覆盖架构到评测 |
| 10 | 已知边界 | 建立信任 | 4 条真实限制 + 评测报告链接 |
| 11 | 演示环境 | 让人能登录 | 账号与口令注入方式（不写死口令） |
| 12 | 许可与合规 | 法务边界 | 私有库、无真实患者数据、NOTICE |

**首屏文案（定稿）**

> 面向医院真实业务的临床协同平台：医嘱闭环 · 医保结算 · 电子病历 · 主数据治理 ·
> AI 循证问答 · 私有化交付。

**"为什么值得读"五条（每条一句结论 + 一句证据）**

1. 领域边界可部署：16 服务 × 独立 schema × 312 个迁移；
2. 关键业务有闭环：医嘱到执行、危急值到通知、告警到工单，均有端到端脚本；
3. AI 有拒答能力：境外端点与模型不一致在生产环境拒绝启动；
4. 门禁真的在跑：pre-push + 11 个 CI job + 2,140 项 Python 测试；
5. 安全默认拒绝：开发密钥/默认口令/未绑定许可任一命中即拒绝启动。

## 4. 仓库主页设置（与 README 同等重要）

| 项 | 建议值 |
|---|---|
| Description | `医院级临床协同平台 · 16 服务 / 913 API / FHIR R4 / AI 循证问答`（≤120 字符） |
| Website | 暂无则留空（不要填 127.0.0.1） |
| Topics | `healthcare` `hospital-information-system` `spring-boot` `vue3` `fastapi` `fhir` `hl7` `medical-informatics` `multi-tenant` `audit-log` |
| Social preview | 用 hero.svg 导出 1280×640 PNG（GitHub 只接受 PNG/JPG） |
| About 勾选 | Releases / Packages 视情况；**不要**勾 "Used by"（无意义） |
| 默认分支 | `main`，开启分支保护（见 `docs/ci/BRANCH-PROTECTION.md`） |
| Releases | 首个 `v1.0.0` 附架构图与评测摘要，不贴内部缺陷清单 |

## 6. 发布节奏（建议）

| 阶段 | 动作 | 验收 |
|---|---|---|
| P0（本次） | 私有仓库 + 历史清理 + README 草稿 | `git log` 无病例/密钥；README 渲染正常 |
| P1 | 补齐截图与 hero.png，替换根 README | 首屏 30 秒可读；所有链接可点 |
| P2 | 打通 Actions，首个全绿 run | 11 个 required checks 全绿 |
| P3（可选） | 转公开：先过 `docs/skills-audit` 版权与内部评审材料复核 | 法务/商务确认 |

## 7. 反面清单（明确不做）

- 不做"Star 求关注"式营销文案；
- 不把评测分数写成"优秀"（真实是 65.9/100，写出来反而可信）；
- 不贴无法复现的性能数字（如"支持 10 万并发"）；
- 不使用真实医院/患者名称做示例；
- 不在 README 放个人邮箱/微信/手机号（用 Issues 模板承接）。
