## 零、一句话结论

**运行时最大的三个风险：**

1. **504 是网关 `response-timeout` 的必然产物，且失败路径完全裸奔。** 网关对 9 条 v2 路由硬编码 `response-timeout: 30000`（`platform/gateway/src/main/resources/application.yml:43-45` 等），SCG 5.0.4 的 `NettyRoutingFilter.getResponseTimeout()` 确实读取路由 `metadata.response-timeout`（字节码实证：读 `Route.getMetadata()` → `Duration.ofMillis`），超时后 `Flux.timeout` 抛出 `TimeoutException` 并被 `lambda$filter$7` 映射为 `HttpStatus.GATEWAY_TIMEOUT`（字节码实证）。**但这条路径不走 `ApiResponse` 壳**：网关只有 `GatewayResponses.reject`（`:31-45`）用于鉴权/限流/404，504 走 Spring 默认错误处理，响应体形如 `{"timestamp":…,"status":504,"error":"Gateway Timeout","path":…}`，**无 `code`/`message`/`traceId`**。前端 `http.ts:116-119` 遇到非 `code===0` 的响应会取 `env?.message`，此时 `env` 为 `null` → 医护看到的是英文字符串 **"请求失败（HTTP 504）"**，且拿不到 traceId，无法自助定位。

2. **网关没有任何熔断/降级，且下游连接池未配置 → 慢下游会被放大成整条路由族 504 风暴。** 网关只装了 Sentinel 的**限流**规则（`SentinelGatewayConfig.java:58-67` 只 `FlowRuleManager.loadRules`），**没有任何 DegradeRule / CircuitBreaker**；`application.yml` 全文**没有 `spring.cloud.gateway.server.webflux.httpclient.*` 任何一项**（SCG 5.0.4 的正确前缀见 `spring-configuration-metadata.json`：`spring.cloud.gateway.server.webflux.httpclient.pool.*`，旧前缀 `spring.cloud.gateway.httpclient.*` 在本版本**不存在**，实测计数为 0）。于是走 SCG 默认值：连接池类型 `ELASTIC`、`maxConnections = max(availableProcessors,8)×2`、`acquireTimeout = 45000ms`（`reactor-netty-core-1.3.8` 的 `ConnectionProvider` 字节码实证：静态初始化读 `reactor.netty.pool.maxConnections`/`acquireTimeout` 默认 `"45000"`）。**acquireTimeout(45s) > response-timeout(30s)**：池满时请求排队等连接，30s 处被统一截断成 504，而排队请求仍占着 Netty worker 与 pending 计数，形成"越慢越排队、越排队越多 504"的正反馈。本机 20 逻辑核 → 默认池仅 **40 条**连接。

3. **前端 `http.ts` 完全没有请求超时、没有取消、没有重试上限 → 挂死页面 + 旧响应覆盖新数据 + 非幂等写操作可能被重放。** `http.ts:87-92` 的 `fetch` 只透传 `opts.signal`，但**全仓无任何调用方传入 `signal`**（`api/index.ts` 的 13 个 `get()` 调用全部只传 `path`/`query`），且没有任何 `AbortController` 实例化，也没有 `setTimeout` 兜底。因此：① 一个慢请求会让页面无限期停在 `loading`（`SurgeryBoardView.vue:337`）；② `SurgeryBoardView.applyDay()`（`:475-483`）在切换日期时**不取消上一轮请求**，旧日期的 `loadDay()` 若后返回会覆盖 `schedulesByRoom`，出现"看的是 B 日、显示的是 A 日台次"；③ `http.ts:108-114` 在 401 后**无条件重放整条请求**（含 POST body），对非幂等接口是一次潜在重复写。

### 1.2 可验证的定位步骤（全部只读）

**Step 1 — 先确认 504 由谁发出（区分网关 504 / 业务 500 / Ingress 504）**

看响应体形状，这是最快的一刀：

```powershell
# 网关 504（Spring 默认错误体，无 code/traceId）
Invoke-WebRequest -Uri "http://127.0.0.1:8080/api/v2/clinical/operating-rooms/<roomId>/schedules?date=2026-11-02" `
  -Headers @{ Authorization = "Bearer <token>" } -SkipHttpErrorCheck |
  Select-Object StatusCode, Content
```

* 网关 504 → `{"timestamp":"…","status":504,"error":"Gateway Timeout","path":"/api/v2/clinical/…"}`
* 业务 500 → `{"code":50000,"message":"系统处理异常…","timestamp":"…","traceId":"…"}`
* Ingress-nginx 504 → HTML 页面

**Step 2 — 定位是哪个 uri 超时**

网关已暴露 `spring_cloud_gateway_requests_seconds`（实测本机有 `routeId`/`routeUri`/`httpStatusCode` 标签，见 `/actuator/prometheus`）：

```
sum by (routeId, httpStatusCode) (rate(spring_cloud_gateway_requests_seconds_count{component="gateway"}[5m]))
```

> 注意：现网告警用的是 `http_server_requests_seconds_count{component="gateway", status=~"5.."}`（`deploy/observability/alerts/medassist-alerts.yaml:71`），但**网关 504 由 `ResponseStatusException` 产生，是否被计入 `http_server_requests` 的 `status` 标签需要实测**（本机实测 `http_server_requests_seconds_count` 的 `uri` 标签全是 `"UNKNOWN"`，无法区分路由 → 这本身就是可观测性缺陷，见 E-P1-05）。

**Step 3 — 区分"下游慢"还是"网关池排队"**

临时把目标路由 `metadata.response-timeout` 从 30000 改成 60000 重发同一请求：

* 变慢但**不再 504** → 下游确实慢（走 R2/R5/R6），先治下游；
* **仍是 504** 或变成 500/503 → 网关连接池/熔断问题（走 R3/R7）。

**Step 4 — 数据库侧取证（只读）**

```sql
-- 慢语句 Top（需 pg_stat_statements 已启用）
SELECT queryid, calls, mean_exec_time, query
FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 20;

-- 锁等待（对应 R6）
SELECT pid, state, wait_event_type, wait_event, left(query,120)
FROM pg_stat_activity WHERE state='active' AND wait_event_type='Lock';

-- 事务里混了远程调用 → idle in transaction
SELECT pid, now()-xact_start AS xact_age, left(query,120)
FROM pg_stat_activity WHERE state='idle in transaction' AND xact_start < now() - interval '10 seconds';
```

**Step 5 — 连接池**

```
hikaricp_connections_pending{component="clinical"}      # 已有告警 MedassistDbPoolPending
hikaricp_connections_timeout_total{component="clinical"}
hikaricp_connections_max{component="clinical"}
```

**Step 6 — 前端扇出**

浏览器 DevTools → Network → 打开排台页 → 数同域并发条数与 `Time to First Byte`。若看到 40+ 条并发小请求、部分 `Time` > 5s，即命中 R4。

**Step 7 — 确认是不是网关连接池耗尽**

当前**无法观测**（见 E-P1-06）。修好 R3 的配置后，网关 `/actuator/prometheus` 应出现 `reactor.netty.pool.pending` / `reactor.netty.pool.acquired`；届时用

```
max_over_time(reactor.netty.pool.pending{component="gateway"}[5m])
```

直接判定池饱和。

### [E-P0-02] `http.ts` 完全没有请求超时与取消机制 → 504 后页面永久挂死
- **位置**：`frontend-console/src/api/http.ts:80-122`（`once`）、`:129-131`（`get`）
- **现象/证据**：`fetch` 调用（`:87-92`）只传 `opts.signal`，而 `RequestOptions.signal`（`:55`）**全仓无任何调用方使用**——`api/index.ts` 的 13 个 `get()` 调用（`:43,46,47,52,53,54,56,57,61,72,73,76,81,82,89,90,97,99,101,103,106,110,118,119,125,126,127,129,130,133,135`）全部只传 `path`/`query`；`http.ts` 内**没有 `AbortController` 实例化、没有任何 `setTimeout` 兜底**。网关 `response-timeout: 30000` 到期后返回 504，前端能收到；但若网关因连接池排队而**不返回任何响应**（连接被占满，Netty worker 阻塞），前端 `fetch` 将无限期挂起。
- **影响**：用户看到白屏/骨架屏永不停（`SurgeryBoardView.vue:31-37` 的 skeleton、`:337` 的 `loading=true`），只能刷新页面。在弱网院内环境（Wi-Fi 漫游、移动推车）这是最常见的"页面卡死"投诉，且此时**用户往往重复点击**（加剧 F1 的扇出）。
- **建议改法**：在 `http.ts` 内统一加超时：`const ctrl = new AbortController(); const timer = setTimeout(() => ctrl.abort(), timeoutMs)`，`timeoutMs` 默认 **35_000**（> 网关 30s，让网关的 504 先到并给出可读文案），查询类可用 15s。`opts.signal` 已存在，用 `AbortSignal.any([opts.signal, ctrl.signal])` 合并外部取消信号。视图层在 `onBeforeUnmount` 里 `ctrl.abort()`。
- **验收方式**：DevTools → Network 勾选 "Preserve log"，把网关 down 掉或让某接口 hang >35s，断言：① 请求在 35s 内以 `AbortError` 结束；② 前端提示"请求超时，请稍后重试"而非永久 loading；③ 组件卸载后进行中的请求被取消（Network 里显示 cancelled）。

### [E-P0-03] 切换日期时旧请求不取消、不校验版本 → 旧日期数据覆盖新日期
- **位置**：`frontend-console/src/views/SurgeryBoardView.vue:475-483`（`applyDay`）、`:485-495`（`watch(route.query.date)`）、`:336-348`（`loadAll`）、`:350-393`（`loadDay`）

### [E-P0-05] 网关连接池未配置，`acquireTimeout(45s) > response-timeout(30s)` → 排队期被截断成 504 雪崩

          webflux:

              connect-timeout: 3000
              response-timeout: 20s

                type: fixed
                max-connections: 256
                acquire-timeout: 2000      # 必须 << response-timeout

- **现象/证据**：JDBC URL 为 `jdbc:postgresql://${PG_HOST}:${PG_PORT}/${PG_DATABASE}`，**无 `socketTimeout`/`statementTimeout`/`ApplicationName`**（全仓 grep 无匹配）。Hikari `maximum-pool-size: 10`、`connection-timeout: 5000`、`minimun-idle: 2`。实测 `/actuator/prometheus` 有 `hikaricp_connections_pending` / `hikaricp_connections_timeout_total` / `hikaricp_connections_acquire_seconds_max`（当前本机最大 acquire 仅 1.5ms，尚未打满）。全仓 `@Transactional` **无一处带 `timeout`**（grep `transactionTimeout`/`@Transactional(timeout` 零匹配）。

- **验收方式**：人为跑一条 sleep 30s 的 SQL，断言在 25s 被中断（客户端收到 `canceling statement due to statement timeout`）且 Hikari 连接被释放；观察 `hikaricp_connections_pending` 不持续 > 0。

### [E-P1-01] 超时预算倒挂：网关 30s > 服务间调用 2–3s，但前端无预算、下游无预算
- **位置**：`platform/clinical/src/main/resources/application.yml:46,51,56`（`EMPI_TIMEOUT:PT2S`、`PHARMACY_TIMEOUT:PT3S`、`TECH_TIMEOUT:PT3S`）、`platform/gateway/src/main/resources/application.yml:45`（30000ms）

- **建议改法**：① 把 4 个 `logback-spring.xml` 里的 `<logger name="com.medassist" level="DEBUG"/>` 改为 `INFO`（或直接删除该行，由 `application.yml` 单一来源控制）；② 为 pharmacy/tech/emr/insurance/kb 补齐同样的 `logback-spring.xml`（含 `[%X{tid:-}]`）；③ `platform/Dockerfile` 增加一个 `-Dmedassist.strict-profiles` 断言，或在 `application.yml` 中对 `dev` profile 加"仅本地"校验（检测到 `spring.profiles.active=dev` 且非本地主机时拒绝启动）。
- **验收方式**：本机以 `--spring.profiles.active=dev` 启动 clinical，断言 `com.medassist` 级别为 INFO（或按预期）；9 个服务的日志行格式一致且都含 traceId 段。

### [E-P1-08] 生产 JVM 堆上限与容器内存限制不匹配，且无 `-XX:MaxDirectMemorySize`
- **位置**：`deploy/helm/medassist-platform/templates/_helpers.tpl:82`（`-XX:MaxRAMPercentage=75`）、`values-prod.yaml:86-87`（gateway `limits: {cpu: "2", memory: 1536Mi}`）、`values.yaml:250-252`（默认 gateway `limits: {cpu: "1", memory: 1Gi}`）
- **现象/证据**：`-XX:MaxRAMPercentage=75` 意味着堆 = 容器 limit × 75%。prod gateway 1536Mi → 堆约 **1152Mi**；**但 `-XX:MaxDirectMemorySize` 未设置**（grep 无匹配）→ 直接内存默认等于堆上限（1152Mi），再加元空间（实测本机 clinical `Metaspace` 已用 **67.6MB**，`CodeHeap 'profiled nmethods'` **25.2MB**）+ 线程栈 + Netty 堆外缓冲，**实际 RSS 可能超出 1536Mi 容器限制 → OOMKilled**。本机实测 `jvm_memory_max_bytes{area="heap",id="G1 Old Gen"} = 4.15GB`（本机无容器限制时），`jvm_threads_peak_threads = 65`。
- **影响**：内存受限的 Pod 被 OOMKill（SIGKILL，无 Java 堆栈）→ K8s 重启 → 滚动发布窗口内表现为**连接被拒/503**而非优雅 504，且 `preStop sleep 10` 的摘流也来不及。`MedassistPodRestarting` 告警（`medassist-alerts.yaml:49-57`）会捕捉到，但根因不易定位。
- **建议改法**：① 显式加 `-XX:MaxDirectMemorySize=256m`；② `-XX:MaxRAMPercentage` 降到 **60–65**（给堆外留足）；③ 加 `-XX:+HeapDumpOnOutOfMemoryError` + `-XX:HeapDumpPath=/tmp`（容器 `/tmp` 是唯一可写卷，见 `deployment-gateway.yaml:128-129`）；④ 内存 limit 建议 `requests × 2`（prod gateway 1536Mi → 考虑提到 2Gi）。
- **验收方式**：压测中观察 Pod `memory.working_set` 峰值 vs limit；断言容器内 `jvm_memory_used_bytes{area="heap"}` 峰值不超过 limit 的 55%。

### [E-P1-09] `docker-compose.yml` 的 `depends_on` 只等启动、不等就绪，且缺 `restart` 策略
- **位置**：`docker-compose.yml:145-147`（`app` depends_on milvus/postgres）、`:54-56`（milvus depends_on etcd/minio）、`:98-99`（attu depends_on milvus）
- **现象/证据**：全部使用**短语法列表形式**（`depends_on: [milvus, postgres]`），只保证"启动顺序"，**不等待健康**。对比 `docker-compose.prod.yml:70-72` 的 nacos 用的是长语法 `condition: service_healthy` —— 说明**同一仓库两种写法不一致**。且 `etcd`/`minio`/`redis`/`nacos` 定义了 healthcheck（`:15-19,35-39,85-89,124-129`），但**没有任何服务消费这些 healthcheck**。`postgres` 服务**完全没有 healthcheck**（`:58-71`）。`app` 服务有 `profiles: ["full"]`（`:133`），默认不启动。

### [E-P1-12] `SurgeryBoardView` 的 `tickTimer` 在 `onBeforeUnmount` 已清理——但 `Promise.all` 未加保护

### [E-P1-15] 网关无请求日志，504 时无法知道是哪个下游、哪个 uri

### [E-P2-01] `docs/OPERATIONS.md` 完全没覆盖 9 个 Java 微服务与网关
- **位置**：`docs/OPERATIONS.md:1-57`
- **现象/证据**：全文 57 行，讲的都是 **Python AI 中台**（`python -m backend.main`、uvicorn workers、Milvus、nginx SSE 配置、`:48-50` 提到 `/healthz` `/readyz` `/metrics`），**完全没有提网关、9 个 Java 服务、Helm、504 排障**。`docs/DEPLOY.md:319-340` 虽有 Kubernetes 章节，但只讲部署形态，不讲运行时排障。
- **影响**：值班同事拿到 504 告警时，没有可执行的 Java 侧排障手册（查哪个日志、哪个指标、怎么区分网关 504 vs 业务 500）——这直接拉长 MTTR。
- **建议改法**：在 `docs/OPERATIONS.md` 增加"Java 平台运行时排障"章节：① 504 定位流程（本文第一章 Step 1–7 可直接复用）；② 9 个服务的端口/日志/actuator 对照表；③ 常见故障与处置（连接池打满、行锁等待、滚动发布切断）。
- **验收方式**：评审时按手册走一遍 504 定位，验证每一步都有明确命令与预期输出。

### [E-P2-02] `logs/` 目录只有 2026-11-01 的 e2e 日志，`svc_*.out.log` 为 0 字节

### [E-P2-05] `docker-compose.yml` 的 `app` 服务无资源限制
- **位置**：`docker-compose.yml:131-147`
- **现象/证据**：`app` 服务只有 `build`/`profiles`/`env_file`/`environment`/`ports`/`volumes`/`depends_on`，**无 `deploy.resources`、无 `mem_limit`、无 `cpus`**。其余服务（etcd/minio/milvus/postgres/redis/nacos）同样无限制，只有 `docker-compose.prod.yml` 的 mysql 有 `restart: unless-stopped`。
- **影响**：本机/试点机上 `app`（含 torch + Milvus 客户端 + 嵌入模型）可能吃满内存，挤压同机 PG；容器无 OOM 优先级的明确约束。
- **建议改法**：给 `app` 加 `mem_limit: 4g` / `cpus: "2"`（对齐 Helm 的 `aiCore` 资源，`values-prod.yaml:178-180`：`cpu 6 / memory 8Gi`）；其余服务也补基础限制。
- **验收方式**：`docker compose ps` 显示内存上限；压测时 PG 容器不被 OOMKill。

### [E-P2-06] 根 `Dockerfile`（Python 中台）无 JVM 相关项但也无资源自检，且 HEALTHCHECK 与 compose 端口绑定不一致的风险
- **位置**：`Dockerfile:42`（HEALTHCHECK 探 `http://127.0.0.1:8001/healthz`）、`docker-compose.yml:141`（`"8001:8001"`）
- **现象/证据**：HEALTHCHECK 与实际端口一致（8001），此处无缺陷。但 `Dockerfile` 无 `STOPSIGNAL`、无 `HEALTHCHECK --start-period` 的合理值（当前 `start-period=60s`，而 `docs/DEPLOY.md:568` 记录 Milvus 模型冷启动可达 **6–10 分钟**、`:585` 记录冷启动要加载 BGE-M3）——`app` 容器在模型加载期间会被判定 unhealthy（Docker 的 `start-period=60s` 之后连续失败即 unhealthy，虽不影响 `depends_on` 但会让运维误判）。
- **影响**：容器健康状态与实际就绪状态不符，排障时误判"app 挂了"。
- **建议改法**：`HEALTHCHECK --start-period=600s`（对齐模型冷启动实测 6–10 分钟）；或让 `/healthz` 在模型未就绪时返回 200 + `status: loading`。
- **验收方式**：冷启动 `app`，断言 10 分钟内健康状态从 starting 转为 healthy，而非 unhealthy。

### [E-P2-07] 网关 `X-Trace-Id` 只写请求头不回写响应头，前后端都没拿到
- **位置**：`platform/gateway/src/main/java/com/medassist/gateway/filter/AuthGlobalFilter.java:75,84`（生成并写入请求头）、`frontend-console/src/api/http.ts:118`（从响应体取 `env?.traceId`）
- **现象/证据**：网关生成 traceId（`:75` `UUID.randomUUID()`）并 `.header(AuthHeaders.TRACE_ID, traceId)`（`:84`）写进**转发的请求**；但**响应头没有回写**（实测 401 响应头无 `X-Trace-Id`）。前端 `ApiError.traceId` 取自**响应体**的 `env.traceId`（`:118`）——而网关生成的错误（401/429/404）走 `GatewayResponses.reject(…, traceId)` **确实带 traceId**（`GatewayResponses.java:42` → `ApiResponse.fail(code, message, traceId)`），但**下游业务服务的错误体里 traceId 为 null**（`AbstractApiExceptionHandler.java:58,70,114,120` 用的是 `ApiResponse.fail(errorCode, msg)`，**不带 traceId**）→ 前端拿到的 `traceId` 大多数时候是 undefined。
- **影响**：链路 ID 在链路上是通的（下游 `TraceMdcFilter` 从 `X-Trace-Id` 请求头取，写入 MDC `tid`，`TraceMdcFilter.java:26-42`），但**客户端拿不到** → 一线报障无法提供 traceId。这是"可观测性"的关键断点。
- **建议改法**：① 网关在响应头统一回写 `X-Trace-Id`；② 下游 `AbstractApiExceptionHandler` 的 `ApiResponse.fail(...)` 补上 traceId（从 MDC `tid` 取）；③ 前端 `ApiError` 优先从响应头 `X-Trace-Id` 取值，body 作为兜底。
- **验收方式**：任意业务错误响应都带 `X-Trace-Id` 响应头与响应体 `traceId`，且两者一致；前端 toast 展示该 traceId。

### [E-P2-08] 网关日志格式与业务服务不一致，无法用统一规则解析
- **位置**：`platform/gateway/src/main/resources/logback-spring.xml:14` vs `platform/auth/src/main/resources/logback-spring.xml:18`
- **现象/证据**：网关格式 `%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [${APP_NAME}] %logger{36} - %msg%n`（**无 `[%X{tid:-}]`**）；auth/clinical/empi 格式 `%d{…} %-5level [${APP_NAME}] [%X{tid:-}] %logger{36} - %msg%n`（**有 tid 段**）。原因已在网关注释里说明（WebFlux MDC 不跨 reactor 线程传播）。
- **影响**：Loki 侧用统一规则抓取时，网关日志会缺一个字段；跨服务 grep 同一 traceId 时网关侧命中不了（只有 `AuthGlobalFilter` 的消息内嵌 `traceId=` 可匹配）。`deploy/observability/loki/promtail-config.yaml` 与 `deploy/observability/alerts/medassist-alerts.yaml:5-10` 都假定日志可按 traceId 检索。
- **建议改法**：网关在 `GlobalFilter` 里手动 `MDC.put("tid", traceId)`（WebFlux 中 `exchange` 作用域内 MDC 可用，但需用 `contextWrite`/装饰器传递），或在日志 message 里统一内嵌 `traceId=`（`AuthGlobalFilter` 已是此风格）；把网关日志格式对齐为带 tid 段的版本。
- **验收方式**：一次跨服务调用（网关 → clinical）在两侧日志中都能用同一 traceId grep 到。

### [E-P2-09] `routes` 的 `metadata` 硬编码超时值，无法按环境调整
- **位置**：`platform/gateway/src/main/resources/application.yml:43-45,52-54,64-66,74-76,84-86,94-96,104-106,115-117,126-128`
- **现象/证据**：9 段 metadata 各自硬编码 `connect-timeout: 3000` / `response-timeout: 30000`（kb 为 60000），共 18 个字面量，**无一处使用 `${ENV_VAR}`**（对比同文件其他配置大量使用 `${NACOS_DISCOVERY_ENABLED:false}` 风格）。
- **影响**：不同院区（门诊量、术间数、AI 中台算力）无法调整超时；调整需改代码 + 重新构建镜像 + 滚动发布，紧急止血（发现 504 后想临时放宽超时）成本高。
- **建议改法**：改为 `${GATEWAY_CONNECT_TIMEOUT_MS:3000}` / `${GATEWAY_RESPONSE_TIMEOUT_MS:30000}`，kb 路由单独 `${GATEWAY_KB_RESPONSE_TIMEOUT_MS:60000}`；配合 `values-prod.yaml` 的 `gateway.env` 注入（该机制已存在，`values.yaml:266-271`）。
- **验收方式**：用 `-DGATEWAY_RESPONSE_TIMEOUT_MS=60000` 启动网关，断言慢请求在 60s 才 504。

### [E-P2-10] `SurgeryBoardView` 导出 CSV 缺元信息，文件名日期与内容可能不一致
- **位置**：`frontend-console/src/views/SurgeryBoardView.vue:627-648`（`exportCsv`）
- **现象/证据**：`exportCsv` 用 `cell.replace(/"/g, '""')` 做了引号转义（`:639`），**这一点是正确的**；但文件名固定为 `手术排台_${day.value}.csv`（`:645`），而导出的内容来自 `sortedRows`（当前 `schedulesByRoom`）。结合 E-P0-03（日期竞态）与 E-P0-10（失败房间回填旧数据），**导出的 CSV 可能包含与文件名日期不一致的台次**——CSV 会被归档进病历，这是合规证据。
- **影响**：导出的排台表可能日期错乱，且没有"数据生成时间/是否含失败房间"的元信息，无法追溯。
- **建议改法**：① 导出前校验 `schedulesByRoom` 中所有排台的日期与 `day.value` 一致，不一致时**拒绝导出并提示**；② CSV 增加首行元信息（生成时间、数据日期、是否含未加载房间）；③ 记录导出审计（谁在什么时候导出了哪天的排台）。
- **验收方式**：在 E-P0-03 的竞态场景下导出，断言导出被拒绝或内容日期一致；CSV 首行含生成时间与数据日期。
