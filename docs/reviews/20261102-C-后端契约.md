## 零、一句话结论

**后端最大的三个问题：**

1. **504 是必然的结构性结果，不是偶发**：网关对每条 v2 路由硬编码 `response-timeout: 30000`，Spring Cloud Gateway 5.0.4 在下游超过该值时把 `TimeoutException` 映射成 `ResponseStatusException(HttpStatus.GATEWAY_TIMEOUT)` 返回 **504**，而下游侧恰好存在多个必然超过 30s 的实现（`hospitalUtilization` 最多 200 次重 CTE 串行、`alerts` 人均 5+ 次查询的 N+1、前端排台页 2N 次并发扇出）。**且 504 响应不走统一 `ApiResponse` 壳、不带 traceId**，前端只能显示"请求失败（HTTP 504）"，运维无法按链路 ID 定位。

2. **契约层三处硬断裂，直接导致临床界面显示错误信息**：排台接口只回 `surgeryCaseId`（无术式/术者/患者号/分级）；排台状态枚举后端是 `SCHEDULED`、前端 `StatusPill` 只映射了 `PLANNED`（界面直接显示英文 `SCHEDULED`）；`SurgeryLevel` 前后端字段名不一致（后端 `surgeryCaseId/appliedBy/reviewedBy` ↔ 前端 `caseId/requestedBy/approvedBy`），申请人/审批人永远显示"—"。

3. **安全与并发两处 P0 级缺口**：① 全平台**没有任何行级/数据级权限**——网关注入的 `X-Org`（科室）在 9 个 Java 服务中**零消费**，任何持 `clinical:surgery:read` 的账号可读取任意手术间、任意患者的排台与术式；② **开台门槛存在 TOCTOU**——`SurgeryService.start()` 对分级/访视/知情同意都是无锁读，而 `SurgeryLevelService.setLevel()` 不与手术行互斥，可出现"三级手术在分级已被改为待审批之后仍被开台"，违反手术分级管理制度。

## 一、504 Gateway Timeout 专项

### 1.1 根因排序（按可能性）

| # | 根因 | 可能性 | 证据（文件:行号） | 说明 |
|---|---|---|---|---|
| R1 | **网关 `response-timeout` 到期直接转 504** | ★★★★★ | `platform/gateway/src/main/resources/application.yml:43-45`（auth）、`:64-66`（clinical）、`:114-117`（kb=60000） | 已从 SCG 5.0.4 字节码实证：`NettyRoutingFilter` 读取路由 `metadata.response-timeout`，`Flux.timeout(...)` 溢出后经 `lambda$filter$7` 构造 `new ResponseStatusException(HttpStatus.GATEWAY_TIMEOUT, ...)` → HTTP **504**。且 `metadata.connect-timeout` 同样被读取（`:43-44` 的 3000ms） |
| R2 | **下游长查询把请求拖过 30s** | ★★★★★ | `TheatreService.java:199-207`（`hospitalUtilization` 循环最多 200 个 ACTIVE 房间，每个房间跑一次 `ClinicalRepository.listRoomDayUsage` 的 `generate_series + 窗口函数 + 2 个相关子查询` CTE，`ClinicalRepository.java:2772-2833`）；`InpatientFinanceService.java:70-82,123-139`（`alerts` 人均 5+ 次查询的 N+1） | 这两条正是网关配置里已经"打了补丁"的接口（`application.yml:193-196` 给 alerts 单独 5 QPS），说明团队已知其昂贵，但**没有消除 N+1**，只是限流 |
| R3 | **网关下游连接池未配置，排队期先被 30s 截断 → 雪崩放大** | ★★★★☆ | `platform/gateway/src/main/resources/application.yml` 全文无 `spring.cloud.gateway.httpclient.pool.*` | 实测默认：`ConnectionProvider.DEFAULT_POOL_MAX_CONNECTIONS = max(Runtime.availableProcessors(), 8) * 2`（8 核 → **仅 16 条**下游连接）、`DEFAULT_POOL_ACQUIRE_TIMEOUT = 45000ms`（reactor-netty 1.3.8）。**acquire 超时 45s > response-timeout 30s**：池满时请求排队等连接，30s 处被统一截断成 504，而排队请求仍占着网关 worker → 一个慢下游能把整个 clinical 路由拖成 504 风暴 |

| R6 | **PG 无 `statement_timeout` / `socketTimeout`，且无慢查询日志** | ★★★☆☆ | `platform/clinical/src/main/resources/application.yml:11`（JDBC URL 无任何超时参数） | 单条失控 SQL（无索引的关联、窗口函数）可无限占用一条 Hikari 连接，直接喂给 R5 |
| R7 | **行锁等待跨事务阻塞** | ★★★☆☆ | `BillingService.java:313-331`（`lockVisit` → `lockCharge`）、`SurgeryChargeService.java:77-111`（`lockVisit` → `lockOpenCharge`）、`NursingService.java:61-63` | 代码注释已自认"settle/dailyBill/discharge 均持有 visit 行锁"。被锁请求一直挂着 → 30s 后 504 |

| R9 | **滚动发布期在途请求超 30s** | ★★☆☆☆ | `platform/gateway/src/main/resources/application.yml:3-4`（graceful）、`values-prod.yaml:79`（gateway 3 副本）、`terminationGracePeriodSeconds: 30` | `terminationGracePeriodSeconds` 与 `response-timeout` 同为 30s，摘流与超时同刻，长请求必被切断成 504 |

### 1.2 可验证的定位步骤（建议值班同事照此执行，全部为只读操作）

**Step 1 — 先确认 504 到底是谁发的（区分网关 504 vs 业务 500 vs Ingress 504）**

看响应体形状：

* 网关 SCG 产生的 504：Spring 默认错误体，形如
  `{"timestamp":"...","status":504,"error":"Gateway Timeout","path":"/api/v2/clinical/..."}`
  —— **没有** `code`/`message`/`traceId` 字段。
* 业务服务产生的错误：统一壳 `{"code":50000,"message":"系统处理异常…","timestamp":"…"}`。
* Ingress-nginx 产生的 504：HTML 页面。

命令（只读 GET）：

```powershell
# 用真实令牌打一次排台接口，观察状态码与响应体形状
Invoke-WebRequest -Uri "http://127.0.0.1:8080/api/v2/clinical/operating-rooms/<roomId>/schedules?date=2026-11-02" `
  -Headers @{ Authorization = "Bearer <token>" } -SkipHttpErrorCheck | Select-Object StatusCode, Content
```

**Step 2 — 找出是哪个 uri 在超时**

```
# 网关侧
sum by (uri,status) (rate(http_server_requests_seconds_count{component="gateway",status="504"}[5m]))
histogram_quantile(0.99, sum by (le,uri) (rate(http_server_requests_seconds_bucket{component="gateway"}[5m]))) > 20
# 临床侧（同一 uri）
max_over_time(http_server_requests_seconds_max{component="clinical",uri="/clinical/operating-rooms/{roomId}/schedules"}[5m])
```

**Step 3 — 区分"下游慢"还是"网关池排队"**

临时把该路由 `metadata.response-timeout` 调到 60000 重发：

* 变慢但**不再 504** → 下游确实慢（走 R2/R6/R7），先治下游；
* **仍是 504** 或变成 500/503 → 网关连接池/熔断问题（走 R3/R8）。

**Step 4 — 数据库侧取证（只读）**

```sql
-- 慢语句 Top
SELECT queryid, calls, mean_exec_time, query
FROM pg_stat_statements ORDER BY mean_exec_time DESC LIMIT 20;
-- 锁等待
SELECT pid, state, wait_event_type, wait_event, left(query,120) FROM pg_stat_activity
WHERE state='active' AND wait_event_type='Lock';
-- 未结束的 idle in transaction（事务里混了远程调用时会看到）
SELECT pid, now()-xact_start AS xact_age, left(query,120) FROM pg_stat_activity
WHERE state='idle in transaction' AND xact_start < now() - interval '10 seconds';
```

**Step 5 — 连接池**

```
hikaricp_connections_active{component="clinical"} / hikaricp_connections_max{component="clinical"}
hikaricp_connections_pending{component="clinical"}     # 已有告警 MedassistDbPoolPending
```

**Step 6 — 前端扇出**

浏览器 DevTools → Network → 打开排台页 → 统计同域并发请求条数与 `Time to First Byte`。若看到 40+ 条并发小请求、且部分 `Time` > 5s，即命中 R4。

### 1.3 结构性修法建议

**网关层**

1. 把 `response-timeout` / `connect-timeout` 从硬编码改为**环境变量可调**（`${GATEWAY_RESPONSE_TIMEOUT_MS:30000}`），并**补一条全局兜底** `spring.cloud.gateway.httpclient.response-timeout`——当前若有人新增路由漏配 `metadata`，该路由就是"永不超时"，请求会挂到浏览器断开为止。
2. **显式配置连接池**（本条最关键）：

   ```yaml
   spring:
     cloud:
       gateway:
         httpclient:
           pool:
             type: fixed
             max-connections: 256      # 覆盖默认 max(cpu,8)*2=16
             acquire-timeout: 2000     # 必须 << response-timeout，让"拿不到连接"快速失败
             pending-acquire-max-count: 512
           connect-timeout: 3000
   ```
   语义：连接池饱和时应在 **2s** 内快速失败（映射 503），而不是排队 45s 后统一变成 504。
3. **补熔断/降级**：用 Sentinel DegradeRule（或 Resilience4j）为 `/api/v2/clinical` 配慢调用/异常比例熔断（RT 阈值 = response-timeout 的 60%，例如 18s），熔断期直接 503，不占连接。
4. **统一网关级错误壳**：新增 `GatewayErrorWebExceptionHandler`（`@Order(-1)`），把 `ResponseStatusException`（含 504）转成 `ApiResponse.fail(ErrorCode.UPSTREAM_TIMEOUT, "…", traceId)`，并**把 `X-Trace-Id` 回写到响应头**（现在只写请求头，客户端拿不到）。
5. `terminationGracePeriodSeconds`（现 30s）必须 **> response-timeout**（建议 45~60s），否则滚动发布必然切断长请求。

**临床服务层**

6. `hospitalUtilization` 改为**一条按 `room_id` 分组聚合的 SQL**（把 `listRoomDayUsage` 的 CTE 改写成 `GROUP BY room_id, day_start` 的单条查询），消除最多 200 次串行 CTE。
7. `alerts` 改为**集合聚合**（一条 SQL 用 `LEFT JOIN + GROUP BY` 一次算出未结/待计/预交金/缺口），消除 N+1。
8. Hikari：`maximum-pool-size` 提到 20~30（prod 3 副本共 60~90），`connection-timeout` 降到 3000，并把 `leak-detection-threshold` 设成 60000。
9. JDBC URL 加超时护栏：`jdbc:postgresql://…?socketTimeout=30&statementTimeout=25&ApplicationName=clinical`，让失控 SQL 在 25s 内被 PG 中断而不是无限占连接。
10. 排台聚合接口加**独立短超时与部分降级**：聚合查询超 5s 时返回 `{ "degraded": true, "rooms": [...部分...] }` 而不是整体 504。
11. 加慢请求日志（>3s 打印 uri + traceId + 耗时 + 操作者），当前只有 `http_server_requests` 聚合指标，无法定位单条慢 SQL。

**前端层**

12. 排台页改为"1 次看板 + 1 次利用率"（见第二章批量接口），去掉 2N 扇出。
13. `frontend-console/src/api/http.ts` 增加请求级超时（`AbortController`，默认 35s > 网关 30s），并对 504 给出医护可读文案（"系统繁忙，请稍后重试"），而不是"请求失败（HTTP 504）"。

### 2.3 必须 join 的表

| 表 | 取的字段 | join 方式 |
|---|---|---|
| `clinical_svc.surgery_schedule` | `id, surgery_case_id, room_id, planned_start, planned_end, sequence, status, cancel_reason, version` | 主表 |
| `clinical_svc.surgery_case` | `case_no, visit_id, patient_id, operation_code, operation_name, surgeon, assistant, anesthesia_type, asa_grade, incision_level, status` | `JOIN surgery_case ON surgery_case.id = surgery_schedule.surgery_case_id`（1:1，必 join） |
| `clinical_svc.visit` | `visit_no, patient_no, dept_id, doctor_id` | `JOIN visit ON visit.id = surgery_case.visit_id` —— **患者号取 `visit.patient_no` 快照**，不跨 schema join `empi_svc.patient`（V1 迁移注释明确"患者主索引归 EMPI，本 schema 只存 patient_id 引用与 patient_no 快照"） |
| `clinical_svc.surgery_level` | `level, approval_status, applied_by, applied_at, reviewed_by, reviewed_at, reject_reason` | **`LEFT JOIN`**（未分级是正常状态，不能 inner join 丢台次） |
| `clinical_svc.operating_room` | `code, name, location, status` | 批量接口里由房间列表侧带出；单房间接口可 `JOIN` |

索引现状已足够：`ix_schedule_room_time (room_id, planned_start)`、`ix_schedule_room_active (room_id, planned_start, planned_end) WHERE status <> 'CANCELLED'`（V18:78-80）、`surgery_level.surgery_case_id UNIQUE`、`surgery_case.visit_id` 有 `ix_surgery_case_visit`。**建议补一条** `CREATE INDEX ON clinical_svc.surgery_case (visit_id, id)` 或直接在 join 计划上确认 `surgery_case.id` 是主键即可（PK 足够）。**不要新增 `surgery_case.patient_id` 索引**——本查询不按 patient_id 过滤。

### 2.4 必须同时处理的一致性问题

| 维度 | 处理要求 |
|---|---|
| **排序** | 服务端固定 `ORDER BY planned_start ASC, sequence ASC, id ASC`（加 `id` 决胜列，防同刻台次抖动导致前端"行跳"）。台次号必须与时间序一致（见 P0-05） |
| **分页/上限** | 单房间单日天然有界；但批量接口必须给 `limit`（默认 500、上限 2000）并在响应里回 `total` 与 `truncated:boolean`，**禁止静默截断**（P0-10 的教训） |
| **权限过滤（接口级）** | 读 `clinical:surgery:read`（沿用现有）；批量接口与单房间接口同一权限点 |
| **权限过滤（数据级）** | ① 必须新增 `X-Org`（科室）的消费：按 `operating_room.dept_id → md_dept.dept_code` 与调用方科室比对，无科室归属的房间仅 ADMIN/手术室角色可见；② **患者号必须按 PHI 规则脱敏**：新增权限点 `clinical:surgery:read_phi`（或复用 `empi:patient:read_phi`），无该权限时 `patientNo` 返回掩码串并置 `patientNoMasked=true`（与 EMPI 掩码口径一致：证件 `前4****后4`、手机 `前3****后4`；患者号建议保留前 4 段、末 4 位掩码） |
| **审计** | 批量看板查询写审计 `SURGERY_BOARD_READ`（detail 只含 `date/roomCount/scheduleCount`，**不得写患者标识**）；带 PHI 权限的明细查询单独记 `SURGERY_BOARD_READ_PHI` |
| **幂等** | 读接口无副作用。**写侧**：排台取消 `CancelScheduleReq.version` 已是 `@NotNull`，前端必须回传 `scheduleVersion`（新 DTO 必须带出 `scheduleVersion`），否则 CAS 失败返回 409 |
| **时间口径** | `plannedStart/plannedEnd` 用 `Instant`（ISO-8601 UTC，如 `2026-11-02T01:00:00Z`）；"当日"参数用 `YYYY-MM-DD`；`BusinessTime.zone()`（Asia/Shanghai）只用于"今天"的默认值与日界切分 |
| **跨零点** | 明确口径：排台与 `[日, 次日)` **有交集**即入该日看板（沿用 `listSchedulesByRoom` 现状），但 `sequence` 的日界按 `planned_start` 落日归属 —— 两者必须在接口文档里写清，否则"台次数"与"排台条数"对不上（见 P1-14） |

### 2.5 前端同步改造的接口契约草案（可直接并行开发）

### [C-P0-06] 网关 30s `response-timeout` 是 504 的唯一来源；且 504 不走统一响应壳、不带 traceId
- **位置**：`platform/gateway/src/main/resources/application.yml:43-45`、`:64-66`（clinical）、`:73-76`、`:80-83`、`:88-91`、`:96-99`、`:104-107`、`:114-117`（kb=60000）、`:120-128`（audit）
- **现象/证据**：所有 v2 路由硬编码 `metadata.response-timeout: 30000`（毫秒）。已从 SCG 5.0.4 字节码实证（`spring-cloud-gateway-server-webflux-5.0.4.jar` → `NettyRoutingFilter.class`）：常量池含 `response-timeout`、`connect-timeout`、`HttpStatus.GATEWAY_TIMEOUT`；反编译片段——
  ```java
  // lambda$filter$7(org.springframework.cloud.gateway.support.TimeoutException)
  new ResponseStatusException(HttpStatus.GATEWAY_TIMEOUT, t.getMessage(), t)
  ```
  即**下游超时必然被网关转成 HTTP 504**。且该异常走 Spring 默认错误处理，响应体是 `{"timestamp":…,"status":504,"error":"Gateway Timeout","path":…}`，**不含** `code/message/traceId`——与平台"统一 `ApiResponse` 契约"（`platform/common/src/main/java/com/medassist/common/api/ApiResponse.java`）相悖。
- **影响**：① 用户看到 HTTP 504（根因见第一章 R2/R4）；② 前端 `frontend-console/src/api/http.ts:116-119` 解析不到 `env.code`，退化为 `env?.code ?? res.status` = 504，`message` 退化为"请求失败（HTTP 504）"——**医护看到技术文案**；③ 响应里没有 `traceId`，运维无法按链路 ID 反查网关/下游日志（网关的 `X-Trace-Id` 只写进了**请求**头，从未回写响应头，见 `AuthGlobalFilter.java:84-86`）；④ `ErrorCode` 枚举里**没有**网关级 5xx 业务码（只有 `INTERNAL_ERROR(50000)`/`UPSTREAM_UNAVAILABLE(50300)`），504 落在体系外。
- **建议改法**：
  1. 超时值改为**环境变量可调**（`${GATEWAY_RESPONSE_TIMEOUT_MS:30000}`），并补全局兜底 `spring.cloud.gateway.httpclient.response-timeout`，避免新增路由漏配变成"永不超时"；
  2. 新增 `platform/gateway/src/main/java/com/medassist/gateway/web/GatewayErrorWebExceptionHandler.java`（`@Order(-1)` 的 `ErrorWebExceptionHandler`），把 `ResponseStatusException`（尤其 504）转成 `ApiResponse.fail(new ErrorCode.GATEWAY_TIMEOUT(50400,"…"), traceId)`；
  3. 在 `AuthGlobalFilter` 里把 `X-Trace-Id` **同时回写到响应头**（`exchange.getResponse().getHeaders().set(...)`），让前端能展示/上报链路 ID；
  4. `ErrorCode` 增补 `GATEWAY_TIMEOUT(50400, "系统繁忙，请稍后重试")` 与 `UPSTREAM_TIMEOUT(50401, …)`；
  5. `frontend-console/src/api/http.ts` 对 504/503 给出医护可读文案（"系统繁忙，请稍后重试"，并提示不要重复提交写操作）。
- **验收方式**：用一个 mock 下游（`Sleeper`）让临床接口延迟 35s，断言网关返回 **HTTP 504 + `ApiResponse` 壳 + `code=50400` + 响应头含 `X-Trace-Id`**；前端错误文案断言为中文业务提示而非"HTTP 504"。

### [C-P0-07] 网关下游连接池完全未配置，默认只有 `max(cpu,8)*2` 条连接，且池等待超时(45s)大于响应超时(30s)
- **位置**：`platform/gateway/src/main/resources/application.yml`（全文无 `spring.cloud.gateway.httpclient.pool.*`、无 `spring.cloud.gateway.httpclient.response-timeout`）
- **现象/证据**：SCG 未配置时使用 `HttpClientProperties.Pool` 默认值 → `type=ELASTIC`、`maxConnections=ConnectionProvider.DEFAULT_POOL_MAX_CONNECTIONS`、`acquireTimeout=ConnectionProvider.DEFAULT_POOL_ACQUIRE_TIMEOUT`。从 reactor-netty 1.3.8（gateway fat jar 内 `BOOT-INF/lib/reactor-netty-core-1.3.8.jar`）`ConnectionProvider.class` 常量池实证：
  * `reactor.netty.pool.maxConnections` 默认 = `Math.max(Runtime.availableProcessors(), 8) * 2` → 8 核机器**仅 16 条**下游连接（9 个微服务共享这一个名为 `proxy` 的池）；
  * `reactor.netty.pool.acquireTimeout` 默认 = `45000` ms。
  即：**池饱和时请求排队最长 45s，而路由的 `response-timeout` 只有 30s**——排在队列里的请求在 30s 处被统一截断成 504，而它仍然占着网关的 Netty worker 与 pending 计数，形成"越慢越排队、越排队越多 504"的正反馈。
- **影响**：一个慢下游（最可能是 clinical 的长查询）即可让**全部** v2 路由排队并集体 504——这与用户观测到的"504"高度吻合，且是**雪崩级放大器**（不是单接口变慢，而是整站变慢）。
- **建议改法**：在 `application.yml` 显式配置（语义：拿不到连接就**快速失败**而不是排队到 504）：
  ```yaml
  spring:
    cloud:
      gateway:
        httpclient:
          pool:
            type: fixed
            max-connections: 256
            acquire-timeout: 2000
            pending-acquire-max-count: 512
          connect-timeout: 3000
  ```
  并配熔断（P1-06）把"池满"转成 503 而非 504；`acquire-timeout` 必须 **显著小于** `response-timeout`。
- **验收方式**：压测（`scripts/loadtest.py` 扩展）并发 200 个慢请求打 clinical，断言网关**快速返回 503**（`ErrorCode.UPSTREAM_UNAVAILABLE`）而不是 504；观察 `reactor.netty.pool.pending` 不持续增长。

### [C-P0-13] 开台门槛（分级审批/术前访视/知情同意）存在 TOCTOU：三级手术可在分级已被改为待审批之后仍被开台
- **位置**：`platform/clinical/src/main/java/com/medassist/clinical/service/SurgeryService.java:88-103`（`start()`：`requireCase` → `repo.lockSurgeryCase`（`FOR UPDATE`）→ `levelService.requireStartApproved(caseId)` → `preopVisitService.requireStartCleared(caseId)` → `requireConsents(caseId)` → `repo.startSurgery(...)`）与 `platform/clinical/src/main/java/com/medassist/clinical/service/SurgeryLevelService.java:54-101`（`setLevel()` 用 `repo.findSurgeryCase` —— **不加锁**，见 `ClinicalRepository.java:2065-2068`；随后 `resetSurgeryLevel` 见 `ClinicalRepository.java:2709-2722`）
- **现象/证据**：

  3. 同理对 `preop_visit`（`conclusion`）与 `surgery_consent`（`revoked_at IS NULL`）做同样的 CAS 断言；
  4. 增加数据库级守卫（可选但推荐）：在 `surgery_case.status` 由 `PLANNED → IN_PROGRESS` 的触发器里直接断言分级/访视/同意条件（把医疗制度写进 DB，与"签署后冻结"触发器同风格）。

### [C-P0-14] 504 由网关生成时不走统一 `ApiResponse` 壳，`ErrorCode` 体系里没有 504 对应业务码，前端只能显示技术文案
- **位置**：网关侧异常路径见 `platform/gateway/src/main/java/com/medassist/gateway/filter/AuthGlobalFilter.java:162-165`（**只有鉴权失败**走 `GatewayResponses.reject` 统一壳）与 `platform/gateway/src/main/java/com/medassist/gateway/web/GatewayResponses.java:31-45`；**超时/熔断/连接池失败**走 Spring 默认错误处理；`platform/common/src/main/java/com/medassist/common/api/ErrorCode.java:15-23`（无 504xx 码）

- **验收方式**：mock 慢下游触发 504，断言响应体形如 `{"code":50400,"message":"系统繁忙，请稍后重试","traceId":"…","timestamp":"…"}` 且响应头含 `X-Trace-Id`；前端断言错误文案为中文业务提示，且 `ApiError.code === 50400`（不是 504）。

## 四、P1 应该优化（20 条）

### [C-P1-01] clinical Hikari 连接池仅 10 条、`connection-timeout 5000`，池满即快速 500
- **位置**：`platform/clinical/src/main/resources/application.yml:14-19`
- **现象/证据**：`maximum-pool-size: 10`、`minimum-idle: 2`、`connection-timeout: 5000`。prod 3 副本（`deploy/helm/medassist-platform/values-prod.yaml:112-120`）共 30 条连接。网关已为 `/api/v2/clinical/inpatient/alerts` 单独限 5 QPS，说明该接口单次占用连接时间很长。
- **影响**：10 条连接被慢查询占满后，第 11 个请求 5s 后抛连接超时 → 500（不是 504），但同时把网关侧变成 R5 触发器；且排台看板的批量接口落地后并发会更高。
- **建议改法**：`maximum-pool-size: 24`、`connection-timeout: 3000`、`leak-detection-threshold: 60000`；并在 Helm values 里按副本数显式配置（`SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE`）；同时把 PG `max_connections` 一并核对。
- **验收方式**：压测下 `hikaricp_connections_pending` 恒为 0；池耗尽时返回 503（`UPSTREAM_UNAVAILABLE`）而不是 500。

### [C-P1-02] JDBC URL 无 `socketTimeout` / `statementTimeout`，PG 侧也没有慢查询日志
- **位置**：`platform/clinical/src/main/resources/application.yml:11`
- **现象/证据**：`url: jdbc:postgresql://${PG_HOST}:${PG_PORT}/${PG_DATABASE}`——无任何超时参数。`platform/common` 与各服务均未配置 `log_min_duration_statement`。
- **影响**：一条失控 SQL（窗口函数、无索引关联）可以无限期占用一条 Hikari 连接（+ 事务），把池拖垮；PG 端也没有可查的慢查询证据，定位只能靠猜。
- **建议改法**：URL 加 `?socketTimeout=30&statementTimeout=25&ApplicationName=platform-clinical`；部署侧在 PG 侧设 `log_min_duration_statement = 500`（或 `ALTER DATABASE … SET`）。
- **验收方式**：人为跑一条 `SELECT pg_sleep(60)`，断言 25s 内被 PG 中断并返回明确错误（而不是挂 60s）。

### [C-P1-03] `InpatientFinanceService.alerts` 是典型 N+1（人均 5+ 次查询），全院 200 人即 1000+ 次
- **位置**：`platform/clinical/src/main/java/com/medassist/clinical/service/InpatientFinanceService.java:70-82`（`alerts`）与 `:123-139`（`buildAlert`：`listCharges` / `listOrders` / `listUnbilledDailyOrders` / `depositBalance` / `findBed`）
- **现象/证据**：每个在院患者 5 次查询，全院 N 人 → 5N 次；网关只能靠 `application.yml:193-194` 的 5 QPS 限流兜。
- **影响**：欠费预警几乎必然超时（→ 504）；限流把"贵"转成"少"，但代价是护士站拿不到预警。
- **建议改法**：改写为 3~4 条集合聚合 SQL（按 `admission_id` 分组的 `LEFT JOIN` + `GROUP BY`），一次算完未结/待计/预交金/缺口；保留现有 5 QPS 限流作为兜底。
- **验收方式**：200 在院患者的库上打一次 `/clinical/inpatient/alerts`，断言 SQL 次数 ≤ 5 且 P99 < 1s。

### [C-P1-04] 跨事务行锁等待：结算/按日计费/退药持 visit 行锁，被锁请求会一路挂到 504
- **位置**：`platform/clinical/src/main/java/com/medassist/clinical/service/BillingService.java:102`（`lockVisit`）、`:202`、`:313`；`platform/clinical/src/main/java/com/medassist/clinical/service/SurgeryChargeService.java:77`；`platform/clinical/src/main/java/com/medassist/clinical/service/NursingService.java:61,137`；`platform/clinical/src/main/java/com/medassist/clinical/service/InpatientService.java:223,330`
- **现象/证据**：锁顺序统一为 `visit → charge`（`BillingService.java:313-331` 的注释自己写明"与 dailyBill / settle 同锁"），这部分是好的。
- **影响**：一次长事务持锁期间，所有同就诊的写请求排队等待；等待时间不可控，最终在网关 30s 处变成 504，且**看起来像"接口慢"而不是"锁等待"**。
- **建议改法**：① 把持锁事务的持锁时间压到最短（锁内不做远程调用——见 P1-05）；② 设置 `lock_timeout`（如 3s）让锁等待快速失败为 409/503 而不是无限等；③ 指标化锁等待（`pg_stat_activity.wait_event_type='Lock'`）。
- **验收方式**：构造两个并发结算请求，断言第二个在 3s 内返回明确错误（不是 30s 后的 504）。

### [C-P1-05] `OrderRefundService` 未取 visit 行锁，与结算不同锁域（与 REVIEW-20261102 P0-12 交叉）
- **位置**：`platform/clinical/src/main/java/com/medassist/clinical/service/OrderRefundService.java:124-148`（直接 `repo.lockCharge(chargeId)`）
- **现象/证据**：退药冲减路径只锁 `charge`，而结算路径是 `visit → charge`；两者对 `charge` 的访问顺序不同 → 既可能读到"结算前的金额"（多退），也可能与 `OrderRefundService.java:136-147` 的 `insertChargeItem` + `addChargeAmount` 交错。
- **影响**：与 `docs/REVIEW-20261102-MULTIAGENT.md` 的 P0-12「退药冲减与结算无共同锁」是同一根因，本次复核确认**仍然存在**。
- **建议改法**：与 REVIEW-20261102 P0-12 合并处理——退药路径补 `lockVisit(order.visitId())`，与结算保持同一锁序。
- **验收方式**：并发退药 + 并发结算的集成测试，断言 `charge.total_amount` 与明细汇总始终相等（`SELECT sum(amount) FROM charge_item WHERE charge_id=?` 对账）。

### [C-P1-06] 网关无熔断/降级规则，慢下游会拖垮整个 `/api/v2/clinical` 路由族
- **位置**：`platform/gateway/src/main/java/com/medassist/gateway/config/SentinelGatewayConfig.java:41-69`（只加载 `FlowRule`）
- **现象/证据**：Sentinel 只用于限流（`RouteRateLimitFilter`），没有任何 `DegradeRule` / 熔断器。
- **影响**：clinical 变慢 → 网关把并发都堆给它 → clinical 更慢 → 其它接口一起超时 → 504 扩散到挂号/收费。
- **建议改法**：为 `/api/v2/clinical`（以及 empi/pharmacy/tech）配置 Sentinel 熔断规则（慢调用 RT 阈值 = response-timeout 的 60%，异常比例 50%，熔断 10s），熔断期快速 503。
- **验收方式**：mock clinical 慢 20s，断言 30s 内熔断生效、后续请求 503 而非 504。

### [C-P1-07] Sentinel 按前缀共享 QPS 桶，排台看板的 2N 请求会误伤挂号/收费
- **位置**：`platform/gateway/src/main/resources/application.yml:180-210`（flow rules）、`platform/gateway/src/main/java/com/medassist/gateway/filter/RouteRateLimitFilter.java:81-88`（`path.startsWith(rule.path())`）
- **现象/证据**：`/api/v2/clinical` 桶 200 QPS，`/api/v2/clinical/inpatient` 60、`/api/v2/clinical/inpatient/alerts` 5——**排台看板没有独立桶**。配置注释自己写了"护理站轮询会吃满 /api/v2/clinical 的共享桶，殃及挂号收费"。
- **影响**：多个用户同时看板 → 挂号/收费被 429；医护在"排台很卡"的同时"挂不了号"，且两个现象互不提示原因。
- **建议改法**：新增 `/api/v2/clinical/surgery` 独立桶（建议 30 QPS）；排台看板改批量接口后请求数降到 1~3，桶压力自然消失。
- **验收方式**：并发 10 个用户各打开一次排台页，断言 `/api/v2/clinical/registrations` 不出现 429。

### [C-P1-08] 缺少 504 / 网关超时 / 连接池等待的专项告警与指标
- **位置**：`deploy/observability/alerts/medassist-alerts.yaml:67-135`
- **现象/证据**：只有 `MedassistGateway5xxRate`（`status=~"5.."`，504 被含在内但无区分）、`MedassistGatewayP99High`（>2s）、`MedassistDbPoolPending`（DB 侧池）。**没有** "504 速率" 专项规则，也**没有** 网关侧下游连接池等待/超时的指标（reactor-netty 的 `reactor.netty.pool.pending` / `acquire.timeout` 未被暴露，SCG 默认 `pool.metrics=false`）。
- **影响**：504 发生时只能靠"5xx 比例"间接感知，且无法区分"下游慢"与"池排队"，值班无法定向排查。
- **建议改法**：① 加 `MedassistGatewayTimeoutRate`（`status="504"` 速率 > 0.1/s 持续 2 分钟 → warning）；② 打开 `spring.cloud.gateway.httpclient.pool.metrics=true` 并加 `reactor.netty.pool.pending > 0` 告警；③ 加 `MedassistClinicalSlowEndpoint`（按 uri 的 P99 > 3s）。
- **验收方式**：在预发布人为触发 504，断言 PrometheusRule 命中且 Alertmanager 收到通知。

### [C-P1-09] `ApiResponse.ok(T)` 永不回填 traceId，成功响应里没有链路 ID
- **位置**：`platform/common/src/main/java/com/medassist/common/api/ApiResponse.java:32-38`（`ok(data)` 传 `null` 作为 traceId）、`platform/common/src/main/java/com/medassist/common/web/TraceMdcFilter.java:30-44`（把 `X-Trace-Id` 只放进 MDC）
- **现象/证据**：网关生成的 `X-Trace-Id` 只进入下游的 MDC（日志里能看到，`logback-spring.xml:10` 的 `%X{tid:-}`），**从不进入响应体**；`ApiResponse` 的 `traceId` 字段在所有成功响应里恒为 null（并被 `@JsonInclude(NON_NULL)` 抹掉）。
- **影响**：用户报障时前端拿不到 traceId，无法把"界面报错"与"日志行"对上；`frontend-console/src/api/types.ts:7` 的 `traceId?: string` 是死字段。
- **建议改法**：加一个 `ApiResponse.ok(data, traceId)` 的调用路径——用 `Tracer`/`MDC.get("tid")` 在 Controller 层自动填（`ApiResponse.ok` 内部读 MDC 即可，无需改所有调用点），并在响应头回写 `X-Trace-Id`。
- **验收方式**：任意 GET 200 响应体必须含 `traceId` 且与响应头 `X-Trace-Id` 一致。

### [C-P1-10] `@JsonInclude(NON_NULL)` 使"空态"响应丢掉 `data` 键，前端拿到 `undefined` 而非 `null`
- **位置**：`platform/common/src/main/java/com/medassist/common/api/ApiResponse.java:23`（`@JsonInclude(JsonInclude.Include.NON_NULL)`）；语义来源 `platform/clinical/src/main/java/com/medassist/clinical/web/SurgeryLevelController.java:34-36`（"GET 在未分级时返回 200 且 data 为空"）与 `PreopVisitController.java:28`
- **现象/证据**：`ApiResponse.ok(null)` → JSON 里**根本没有 `data` 这个键**；前端 `frontend-console/src/api/http.ts:121` 返回 `env.data` = `undefined`。但 `frontend-console/src/api/types.ts:245` 声明的是 `SurgeryLevel | null`。
- **影响**：类型撒谎；任何 `data.xxx` 的直接访问在"未分级/未填写"时抛 `Cannot read properties of undefined`。目前靠各处 `?.` 与 `?? '—'` 侥幸不出错，但**下一个开发者必然踩坑**。
- **建议改法**：二选一——① 保留 `NON_NULL` 但把"空态"改成显式对象（如 `{"exists":false}`）；② 给 `data` 加 `@JsonInclude(ALWAYS)`（或去掉类级 NON_NULL，只对 `traceId` 保留）。同时前端类型改为 `T | null | undefined`。
- **验收方式**：契约测试——对"未分级"的 `GET /clinical/surgery-cases/{id}/level`，断言响应体**显式含** `"data": null`，且前端 `await api.level(id)` 的结果 `=== null`。

### [C-P1-11] `PageResult` 不返回 `totalPages`，前端类型里的 `totalPages?` 是死字段
- **位置**：`platform/common/src/main/java/com/medassist/common/api/PageResult.java:16-21`（只有 `page/size/total/items`）vs `frontend-console/src/api/types.ts:11-17`（`totalPages?: number`）
- **影响**：分页控件无法显示总页数；且 `PageResult` 没有 `truncated` 概念（与 P0-10 同源问题）。
- **建议改法**：后端补 `totalPages`（或统一改用 `total` 自行计算）并去掉前端的可选字段；同时补 `hasNext` 之类的明确字段。
- **验收方式**：契约测试断言 `PageResult` 的 JSON 键集合与 `types.ts` 声明一致。

### [C-P1-12] 手术间/手术/字典等列表接口统一用 `limit` 截断，没有 `total`/`truncated`，存在与 P0-10 同源的静默丢数据风险
- **位置**：`platform/clinical/src/main/java/com/medassist/clinical/service/TheatreService.java:57-61`（rooms）、`platform/clinical/src/main/java/com/medassist/clinical/service/SurgeryService.java:45-48`（catalog，20/100）、`platform/clinical/src/main/java/com/medassist/clinical/web/ReferenceController.java`（科室/收费项目）
- **现象/证据**：多个列表接口返回裸 `List`，截断上限不可见。
- **影响**：与 P0-10 相同的"账上有、界面上没有"风险，只是当前上限还没被触达。
- **建议改法**：统一约定：所有 `limit` 型列表接口必须回 `total` 与 `truncated`（或改用 `PageResult`），并在 `docs/` 里立一条"列表接口契约"规范。
- **验收方式**：新增一个契约测试遍历全部列表接口，断言都带 `total/truncated` 或使用 `PageResult`。

### [C-P1-13] `listRoomDayUsage` 用相关子查询算接台间隙，改成窗口函数一次算完
- **位置**：`platform/clinical/src/main/java/com/medassist/clinical/repo/ClinicalRepository.java:2798-2828`（`gaps` CTE + 两个 `(SELECT … FROM gaps g WHERE g.day_start = j.day_start)` 相关子查询）
- **现象/证据**：同一 `gaps` 被扫描两次；且 `days`/`windows`/`joined` 三层 CTE 在 `LEFT JOIN` 下会产生"无排台日"的一行 NULL（`status IS NULL`），语义正确但写法冗余。
- **影响**：在 92 天窗口 × 200 房间下开销巨大（与 P0-08 叠加）。
- **建议改法**：用 `sum(...) OVER (PARTITION BY room_id, day_start)` 一次算完占用与间隙；配合 P0-08 的单 SQL 分组聚合。
- **验收方式**：断言改写前后同一数据集的 `occupiedMinutes/turnoverMinutes/turnoverCount` **完全相等**（回归用例）。

### [C-P1-14] "当日"口径在排台与利用率之间不一致（跨零点台次归属不同）
- **位置**：`platform/clinical/src/main/java/com/medassist/clinical/repo/ClinicalRepository.java:2316-2327`（排台：与 `[日,次日)` **有交集**即入该日）vs `:2772-2833`（利用率：按 `planned_start` 落日 + 与开放时段取交集）
- **现象/证据**：23:00–01:00 的跨零点排台会出现在**两天**的排台看板上，但其占用分钟被切分到两天；而 `sequence` 只按 `planned_start` 落日计算（`ClinicalRepository.java:2245-2246`）。
- **影响**："当日排台条数"（看板）与"当日占用分钟/台次数"（利用率）口径不同，跨零点手术多的医院（夜间急诊）会明显对不上。
- **建议改法**：把"当日"定义写进契约文档并统一：建议**排台与利用率都用 `planned_start` 落日**（跨零点台次归属到"开始日"），看板另加"跨零点"提示字段；或两者都用"交集"口径并在利用率里按天切分（现状）但把 `sequence` 也按交集口径重算。
- **验收方式**：造一条 23:30–00:30 的排台，断言看板条数、占用分钟、`sequence` 三者在同一天内自洽。

### [C-P1-15] 手术域的审计 JSON 手工拼串，与平台其它服务的 Jackson 范式不一致（P0-12 的根因面）
- **位置**：`SurgeryService.java:171-185`、`SurgeryLevelService.java:202-209`、`SurgeryChargeService.java:212-218`、`TheatreService.java:307-315`、`IntraopService.java:248-256`、`PreopService.java:218`、`PreopVisitService.java:175`
- **现象/证据**：手工 `escape()` 只处理 `"` 与 `\`，不处理控制字符；其余 10 个服务已统一用 `objectMapper.writeValueAsString` + 失败兜底。
- **影响**：同类缺陷分散在 7 个类里，每加一个自由文本字段就多一个雷。
- **建议改法**：在 `platform/common` 提供 `AuditJsonSupport`（注入 `ObjectMapper`，`write(Map)` 失败时返回 `{"_detail_serialize_failed":true}`），所有服务改用它；`escape()` 方法全部删除。
- **验收方式**：静态检查（grep `+"\\"" +` 的手工拼串）零命中；新增单测覆盖特殊字符。

### [C-P1-16] 硬编码的开发口令/JWT 密钥兜底在 `application.yml` 里，且 `.env.example` 缺 Java 平台全部变量
- **位置**：`platform/clinical/src/main/resources/application.yml:13`（`password: ${PG_PASSWORD:<dev-password>}`）、`platform/gateway/src/main/resources/application.yml:152`（`secret: ${JWT_SECRET:<dev-jwt-secret>}`）、`platform/common/src/main/java/com/medassist/common/security/SecurityDefaults.java:22`；`.env.example`（全文只有 Python 栈变量）
- **现象/证据**：`SecurityDefaults.isProduction` 已做"生产用开发密钥则拒绝启动"的守卫（`GatewayAuthConfig.java:49-55`），这一点做得好；但 **PG 口令没有同类守卫**（生产若忘注入 `PG_PASSWORD`，就会用 `<dev-password>` 连上生产库）。`.env.example` 里**完全没有** `JWT_SECRET`、`INTERNAL_API_TOKEN`、`MEDASSIST_ENV`、`SENTINEL_QPS_*`、`PLATFORM_*_URI`、`GATEWAY_*`、`PG_*`（Java 侧）等变量——而 `docs/OPERATIONS.md:20` 明确指示"`cp .env.example .env.local`"。

- **验收方式**：在 `MEDASSIST_ENV=production` 且 `PG_PASSWORD=<dev-password>` 的情况下启动 clinical，断言**拒绝启动**并给出明确报错。

### [C-P1-17] `docs/KEY_ROTATION_DRILL.md` 只覆盖 Python 栈，Java 平台的密钥从未演练
- **位置**：`docs/KEY_ROTATION_DRILL.md`（全文，演练对象是 `medagent_pg`/`medagent_milvus` + FastAPI `127.0.0.1:8001`）；Java 平台密钥面见 `deploy/helm/medassist-platform/values.yaml:103-122`（`internalApi`/`internalHmac`/`jwt`）与 `:196-204`（`secrets.*`）
- **现象/证据**：演练结论表里的"三类凭据全覆盖"指的是 JWT secret（Python）、LLM api_key、DB 密码；**网关 JWT 密钥、`INTERNAL_API_TOKEN`、HMAC/Ed25519 签名密钥、9 个服务的 PG 口令**没有任何一条演练记录。而 `values.yaml:108-122` 的 HMAC 密钥与 `:153-182` 的 Ed25519 切换有明确的"多把并存 + 观察 7 天"流程要求——**没有演练就没有证据**。
- **影响**：文档标题"密钥轮换演练记录"会让读者以为平台密钥轮换已验证；实际上一旦需要紧急轮换网关 JWT 或内部令牌，没有可执行 SOP，且网关与 auth 的密钥必须同步切换（双密钥窗口无自动化）。
- **建议改法**：新增 `docs/KEY_ROTATION_DRILL-JAVA.md`（或在本文件追加"Java 平台"章节），按 `values.yaml` 的注释把每类密钥的轮换步骤、前置条件、回滚路径、验证命令写成可执行清单，并在预发布实跑一次（JWT 双密钥 + 内部令牌滚动 + PG 密码滚动重启 + Ed25519 密钥对替换）。
- **验收方式**：文档中每类密钥都有"演练日期 + 实测结果 + 复跑命令"，且脚本 `scripts/drill_key_rotation.py` 扩展出 Java 分支。

### [C-P1-18] 排台接口无分页/无上限返回（单房间单日有界，但跨零点 + 批量接口后需显式化）
- **位置**：`platform/clinical/src/main/java/com/medassist/clinical/repo/ClinicalRepository.java:2316-2327`
- **现象/证据**：`listSchedulesByRoom` 无 LIMIT，全靠"单房间单日"这一隐含前提约束；一旦支持"整月排台"或"全部房间批量"，会变成无界结果集。
- **影响**：接口形状容易被误用（如前端传一个月的 date 范围）。
- **建议改法**：批量接口强制 `limit`（默认 500、上限 2000）+ `truncated`；单房间接口限制 `date` 跨度（如同 `MAX_RANGE_DAYS=92`，`TheatreService.java:182`）。
- **验收方式**：断言传超范围日期返回 422 而不是大结果集。

### [C-P1-19] clinical 缺慢请求日志与接口级耗时打点，定位不到"哪条 SQL 慢"
- **位置**：`platform/clinical/src/main/resources/logback-spring.xml`（只有 Console appender，无请求日志）、`platform/clinical/src/main/resources/application.yml:74-77`（只设 root INFO）
- **现象/证据**：只有 Spring Boot 自动的 `http_server_requests` 聚合指标（按 uri 聚合，无 traceId、无操作者）；`AbstractApiExceptionHandler.java:119` 只在异常时打全栈。
- **影响**：504 排查时无法把"慢的 uri"定位到"慢的那次调用"；也无法回答"是谁在什么时候触发的"。
- **建议改法**：加一个 `OncePerRequestFilter`（复用 `TraceMdcFilter` 的 MDC）记录 >3s 的请求：uri + traceId + actor + 耗时 + 操作者；并打点 `medassist_slow_request_seconds{uri}`。
- **验收方式**：mock 一个 5s 的接口，断言日志里出现含 uri/traceId/actor 的一行 WARN。

### [C-P1-20] 日志输出只有 Console；`com.medassist` 的级别在两处重复声明，dev profile 会把 DEBUG 打进生产镜像
- **位置**：`platform/clinical/src/main/resources/logback-spring.xml:15-19`（`com.medassist` = DEBUG）与 `platform/clinical/src/main/resources/application.yml:74-77`（`com.medassist` = INFO）；`platform/clinical/src/main/resources/application-dev.yml:18-20`（dev 下 DEBUG）
- **现象/证据**：`logback-spring.xml` 写 DEBUG、`application.yml` 写 INFO，两处冲突（Spring Boot 的 `logging.level.*` 覆盖 logback 文件，所以运行时是 INFO；但**读代码的人会误判**）。生产镜像已用 `-Pprod-package` 排除 `application-dev.yml`（`platform/Dockerfile:45-47`），但**本机 `java -jar` 直接跑 fat jar 时 dev 配置仍在 jar 里**（`logs/e2e_clinical.log:13` 显示 `"dev"` profile 生效、`:12` 有 DEBUG 行）。
- **影响**：本机以默认 profile 跑 jar 时可能开 DEBUG；DEBUG 级第三方日志可能带 SQL 与参数（**PHI 风险**，见下）。生产走容器不受影响，但本机排障环境与生产行为不一致，容易误判。
- **建议改法**：① `logback-spring.xml` 删掉 `<logger name="com.medassist" level="DEBUG"/>`，级别只由 `application.yml` 单点控制；② 本地跑 jar 必须在启动脚本里显式 `--spring.profiles.active=dev`（并把 dev 配置从 jar 中物理排除，或改名为 `application-local.yml`）；③ 补一个 `logs/` 文件 appender（带滚动），或在 docs 里明确"生产日志由 Loki/Promtail 采集 stdout"（`deploy/observability/loki/promtail-config.yaml` 已存在）。
