## 1. 结论摘要

1. **v4 的设计方向已经落地。** 深色侧边栏、KPI 图标与 sparkline、眉标、01–02–03 编号、shimmer 骨架、斑马纹、全大写表头、巨大空态插画、彩色左条——A 路逐项核对后确认**全部已清除**。这条不该再被当成待办。
2. **v4 剩下的设计问题不是"审美"，是可用性。** 控件边框 1.48:1（系统自己定的门槛是 3:1）、390px 下 4 张表仍是可横向滚动的桌面表格、三处临床警示类名没有样式规则。
3. **504 不是偶发，是结构必然。** 网关 `response-timeout: 30000` 硬编码 + 连接池未配置（`acquire-timeout` 默认 45s > 30s）+ 无熔断 + 下游有必然超过 30s 的接口（利用率 N+1 最多 200 次 CTE）+ 前端排台页 2N 并发扇出。五个因素叠在同一条链路上。
4. **504 的呈现方式比 504 本身更糟。** 网关 504 不走统一 `ApiResponse` 壳、无 `code`、无 `traceId`，医护看到的是 `请求失败（HTTP 504）` 这种英文技术串。
5. **最危险的不是崩溃，是静默错。** 收费单请求失败时 `catch` 吞错 → 显示 `¥0.00`；访视页切换病例后 ASA/禁食填进上一个病人；知识库切换空间后旧空间结果留在屏幕上。这三条都属于"看起来正常、其实错了"。
6. **前端 DTO 已与后端漂移，但 typecheck 全绿。** `requestedBy/approvedBy` vs `appliedBy/reviewedBy`、`ampouleReturned` 布尔 vs 整数、`AnswerCitation` 字段缺失——类型本身写错了，所以校验通过不证明契约正确。
7. **全平台没有任何行级数据权限。** 网关注入的 `X-Org` 在 9 个 Java 服务里零消费；改 URL 参数就能读到别的科室的手术与患者数据。
8. **前端请求无超时、无取消、无重试上限。** 页面可以永久挂死；切日期时旧响应会覆盖新数据；401 刷新失败会无限递归重放 POST。
9. **文档已经和代码脱节。** `FULL-READ.md` 声称补读 16 个技能，实际 `full/` 下只有 10 个技能目录，6 个声称存在的文件全仓零命中；`HANDOFF.md` 通篇停在 v2，没有任何 v3/v4 章节。
10. **好消息：术中收费幂等、分级审批 CAS、排台 advisory lock、身份头剥离、PHI 分级暴露、KB 降级路径都已正确实现。** C 路专门列了"已确认不是问题"一章，这些不要再返工。

## 2. P0 必须修改（20 条）

### 组 A｜安全与数据正确性（8 条）

#### [P0-01] 全平台无行级数据权限，跨科室可越权读手术与患者数据
- **位置**：`platform/gateway/src/main/java/com/medassist/gateway/filter/AuthGlobalFilter.java:L137-L152`；`platform/common/.../security/AuthHeaders.java:L38`；`platform/clinical/.../ClinicalRepository.java` 各查询
- **证据**：网关在鉴权后注入 `X-Org` / `X-Dept` 头，但 9 个 Java 服务中 **零消费**——所有 `WHERE` 只带 `id`，不带 `dept_code` / `org_code`。
- **影响**：任何登录用户改 URL 里的 `surgeryCaseId` 即可读到其他科室患者的手术、分级、访视记录。属于《个人信息保护法》意义上的越权访问患者健康信息。
- **建议**：新增 `DataScope` 助手（从 `SecurityContext` 取 org/dept/role），在 Repository 层统一追加 `dept_code IN (...)`；看板/列表接口必须带数据范围；新增 `read_phi` 权限点控制患者号/姓名是否掩码返回。
- **验收**：用 B 科室账号请求 A 科室 `surgeryCaseId` → 必须 403/404，且审计日志有拒绝记录。
- **来源**：C-P0-04

#### [P0-02] 开台门槛 TOCTOU：三级手术可在分级已改为待审批后仍被开台
- **位置**：`platform/clinical/.../SurgeryService.java:L88-L103`（开台读分级无锁）；`SurgeryLevelService.java:L54-L101`（改分级不与手术行互斥）；`ClinicalRepository.java:L2059-L2068, L2709-L2722`
- **证据**：`start()` 先 `SELECT` 分级再判断，`setLevel()` 在另一事务里改分级并提交，两者锁域不重叠。
- **影响**：分级审批是手术安全的硬门槛。存在"审批未过但手术已开台"的窗口，属于医疗安全事件。
- **建议**：统一锁域——`setLevel()` 写路径也 `SELECT ... FOR UPDATE` 手术病例行；`start()` 的门槛判断改为带 `version` 的 CAS 断言；DB 层加触发器做最后兜底。
- **验收**：并发脚本同时执行 `setLevel(3级)` 与 `start()`，压 1000 次，开台成功且分级为 `PENDING` 的次数必须为 0。
- **来源**：C-P0-13

#### [P0-03] 三处临床警示的 CSS 类没有样式规则，警示静默失效
- **位置**：`frontend-console/src/views/PreopVisitView.vue:L64, L69`；`SurgeryChargesView.vue:L82, L87`；`NarcoticRegisterView.vue:L20`；缺失规则在 `frontend-console/src/styles/orders-view.css`
- **规范依据**：`docs/DESIGN-SYSTEM.md` §3.2「`--warning` 待处理/维护」「颜色不是唯一信息」；`08-taste-skill/references/app-screens.md`「Red is a signal, never decoration」
- **现状**：模板上写了 `class="kpi is-warn"` / `class="kpi is-danger"`，但 `.kpi.is-warn .kpi-value`、`.kpi.is-danger` 三条规则在 CSS 里**不存在**。禁食 <6h、不宜手术、待回收空安瓿三个警示与普通数字外观**完全一致**。
- **危害**：术前访视员在 8 小时工作里扫过一屏数字，看不出"这个病人禁食不够"。这是会直接影响手术决策的失效。
- **建议**：补三条规则——`.kpi.is-warn .kpi-value { color: var(--warning) }`、`.kpi.is-danger .kpi-value { color: var(--negative) }`、`.kpi.is-danger { border-left: 0 }` 并加文字标签（不能只靠颜色）。
- **验收**：构造禁食 4h 的病例，截图对比警示项与普通项，色值必须是 `--warning`/`--negative`，且同时存在文字提示。
- **来源**：A-P0-04

#### [P0-04] 收费单请求失败被吞成 `¥0.00`，护士会照着 0 元去结算
- **位置**：`frontend-console/src/views/OrdersWorkbenchView.vue:L1046-L1053`（catch 吞错）；同类 `A-P0-06` 在 `L140, L447`（`?? 0`）
- **规范依据**：`docs/DESIGN-SYSTEM.md` §5.3「空值用灰色破折号；真实 0 打印为 0」；§6「错误：失败块内部一句『什么失败 + 上次成功时间』+ 重试」
- **现状**：`try { preview = await billingApi.preview() } catch { preview = { total: 0 } }`；模板再把 `?? 0` 兜底。接口失败与"应收 0 元"在界面上无法区分。
- **危害**：漏收费、错结算。医疗计费场景里这是财务与合规事故。
- **建议**：新增独立的 `chargeError` 状态；失败时保留上一次成功值并显示"上次成功 HH:mm" + 重试按钮，**不显示 0**；`?? 0` 改为 `'—'`，真实 0 才打印 `0`。
- **验收**：断掉 billing 接口后打开医嘱页——收费区必须显示错误块与重试，不得出现 `¥0.00`。
- **来源**：B-P0-05、A-P0-06

### 组 B｜504 与运行时可用性（8 条）

#### [P0-09] 网关 30s 硬超时 + 504 不走统一错误壳 + 无 traceId
- **位置**：`platform/gateway/src/main/resources/application.yml:L43-L45, L64-L66, L114-L117`；`platform/gateway/.../web/GatewayResponses.java:L31-L45`；`platform/common/.../api/ErrorCode.java:L15-L23`
- **证据**：路由级 `response-timeout: 30000` 硬编码；SCG 5.0.4 到点抛 `ResponseStatusException(GATEWAY_TIMEOUT)`（已用 `javap` 反编译 fat jar 字节码实证）；504 响应体是 Spring 默认体，**没有** `code` / `message` / `traceId`，`ErrorCode` 里也没有 504 码。
- **影响**：① 任何超过 30s 的下游调用必然 504；② 前端 `errorText()` 拿不到业务码，只能拼出 `请求失败（HTTP 504）` 这种技术串给医护看；③ 没有 traceId 无法与后端日志关联，故障无法定位。
- **建议**：① 超时值 env 化（`GATEWAY_RESPONSE_TIMEOUT`），并在 `spring.cloud.gateway.server.webflux.httpclient` 加全局兜底；② 新增 `GatewayErrorWebExceptionHandler`，把 504/503 转成统一 `ApiResponse` 壳并回写 `X-Trace-Id`；③ `ErrorCode` 增加 `GATEWAY_TIMEOUT(50400)`，前端映射成中文可操作文案（"服务响应超时，请稍后重试；若持续出现请联系信息科"）。
- **验收**：用 `curl -m 40` 打一个故意 sleep 35s 的下游，响应必须是 `{code:50400, message:"...", traceId:"..."}`，`Content-Type: application/json`。
- **来源**：C-P0-06、C-P0-14、E-P0-08

#### [P0-10] 网关未配置连接池，`acquire-timeout`(45s) > `response-timeout`(30s)，排队即 504
- **位置**：`platform/gateway/src/main/resources/application.yml`（**整份无** `httpclient.pool.*`）
- **证据**：SCG 5.0.4 + reactor-netty 1.3.8 字节码常量实证——默认 `ConnectionProvider.ELASTIC`，`maxConnections = max(cpu, 8) * 2`（≈16 条），`acquireTimeout` 默认 45000ms。一个慢下游会占满 16 条连接，后续请求排队 45s，**比 30s 的 504 还长**，于是整条路由族集体 504。
- **建议**：显式配置 `spring.cloud.gateway.server.webflux.httpclient.pool`：`type: fixed`、`max-connections: 256`、`acquire-timeout: 2000`（远小于 response-timeout，让"拿不到连接"快速返回 503 而不是排队到 504）；`connect-timeout: 2000`。
- **验收**：用 `wrk` 打 200 并发到一个 sleep 20s 的下游，网关必须在 2s 内对超额请求返回 503，而不是全部挂到 30s 后 504。
- **来源**：C-P0-07、E-P0-05

#### [P0-11] 网关无熔断降级，一个慢下游拖垮整条路由族
- **位置**：`platform/gateway/.../config/SentinelGatewayConfig.java:L41-L69`
- **证据**：只注册了 `FlowRule`（QPS 限流），**没有任何 `DegradeRule`**；也没有 `spring-cloud-starter-circuitbreaker` 依赖。
- **建议**：加熔断——`DegradeRule` RT 阈值 18s（低于 30s 超时）、熔断 10s、半开 3 次；或引入 Resilience4j `CircuitBreaker` GatewayFilter，按路由独立配置。
- **验收**：把 clinical 打慢到 25s 持续 30s，其他路由（empi/kb）的 P99 不得同步劣化。
- **来源**：C-P1、E-P0-07

#### [P0-12] 利用率接口 N+1：单次请求最多 200 次 CTE 查询
- **位置**：`platform/clinical/.../TheatreService.java:L199-L207`；`platform/clinical/.../ClinicalRepository.java:L2772-L2833`
- **证据**：按房间循环调用 CTE 查询，房间上限 200。
- **影响**：这是 504 的第二大根因。12 个房间 × 每次 CTE ≈ 秒级；房间多的院区直接撞 30s。
- **建议**：改写成**一条**按 `room_id` 分组的聚合 SQL（`GROUP BY room_id`），一次返回全部房间的 scheduled/completed/cancelled/occupied/available；Service 层只做映射。
- **验收**：`EXPLAIN ANALYZE` 单次执行 < 200ms；接口 P95 < 500ms（12 房间）。
- **来源**：C-P0-08、E-R2

#### [P0-13] 排台页 2N 并发扇出，放大 504 并挤占其他路由的限流桶
