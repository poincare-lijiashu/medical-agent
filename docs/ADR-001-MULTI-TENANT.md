# 多租户架构决策（ADR-001）：全院级全栈隔离（Cell per Hospital）

- 状态：已决（2026-11-12）
- 决策人：产品/架构（用户确认）
- 关联：计划书 W9.1；`§279 授权与许可`（instanceCode 即租户键）、`§280 开放平台`
- 影响面：auth（租户域）、gateway（路由）、全部业务服务（数据源）、部署编排、运维

## 1. 背景与目标

系统要同时服务多家医院。医疗场景的隔离要求高于普通 SaaS：

- 一家医院的一次错误发布、一条慢 SQL、一次数据库故障，**不得**影响另一家；
- 患者数据不得跨院可见，也不做跨院汇总（合规最简）；
- 医院规模以三甲/二级为主，单院数据量足以支撑"一院一套数据面"的成本；
- 版本必须可分批灰度，能单院回滚。

用户明确要求：**不以便宜/好做为目标，以技术隔离强度为第一目标**。

## 2. 决策（3 条，不再摇摆）

| 编号 | 决策 | 说明 |
| --- | --- | --- |
| D1 | **每个医院一个独立 Cell（全栈 silo）** | 独立数据库实例、独立服务实例组、独立 ingress、独立备份、独立监控；不共享连接池、不共享 schema |
| D2 | **控制面共享，但不在临床读路径上** | 租户目录、身份签发、授权许可、发布编排、监控聚合共享；临床请求只依赖本 Cell 与本地验签 |
| D3 | **不做 tenant_id 行级共享库，也不做跨院汇总** | 物理隔离后不需要 tenant_id（消灭"忘写 where 就串院"的事故面）；集团报表由院方自行导出 |

补充：**campus（院区）保留**。租户=医院（法人/独立部署），院区=同一医院内的多院区，二者是层级关系而非替代关系。

## 3. 隔离契约（这是"完成"的验收定义，不是部署完成即算）

| 维度 | 契约 | 验证方式 |
| --- | --- | --- |
| 数据 | 跨租户读取返回 404/403，任何接口都不例外 | 自动化越权用例：A 院令牌遍历 B 院资源 ID |
| 计算 | A 院故障（进程被杀/持续 100% CPU）时，B 院 P99 波动 ≤ 5%、错误率不变 | 故障注入演练（chaos） |
| 流量 | A 院洪峰不触发 B 院限流 | 单 cell 压测 + 网关分桶 |
| 发布 | 单院回滚不影响其他院；错误版本不跨 cell 扩散 | 分批发布演练：1 家 → 10% → 全量 |
| 备份 | 单院 PITR 只恢复该院；恢复演练不锁其他院数据库 | 每季度单院恢复演练 |
| 身份 | 租户管理员只能管理本租户用户/角色；令牌带 tenant 且不可跨 cell 使用 | 越权用例 + 令牌重放用例 |
| 观测 | 指标/日志/追踪带 tenant 标签，可按院出 SLO | 看板与告警路由抽查 |

RTO/RPO 对三甲单院独立承诺（建议 RTO ≤ 30 分钟、RPO ≤ 5 分钟，随合同定）。

## 4. 逻辑架构

```
                         ┌──────────────────── 控制面（共享，HA，可降级）────────────────────┐
  运营/厂商 ───────────► │ tenant registry · 开通编排 · 身份签发(auth) · 授权许可(license)      │
                         │ 发布编排(release) · 监控聚合 · 计费用量                              │
                         └───────────────┬────────────────────────────────────────────────────┘
                                         │ ① 开通：建库/跑迁移/建命名空间/发 license/建首个管理员
                                         │ ② 发布：按 cell 灰度，不改临床读路径
        DNS: hospital-a.example ─────────┤
                                         ▼
   ┌──────────────────── Cell A（市一院）────────────────────┐   ┌──────── Cell B（市二院）────────┐
   │ ingress → gateway(A) → 业务服务组(A) → PostgreSQL(A)     │   │ ingress → gateway(B) → …        │
   │ 独立 namespace / ResourceQuota / NetworkPolicy / PDB     │   │ 独立 namespace / 独立 PG 实例    │
   │ 独立备份与 PITR / 独立 Prometheus 抓取 / 独立日志流       │   │ …                               │
   └──────────────────────────────────────────────────────────┘   └─────────────────────────────────┘
```

读路径（挂号、开医嘱、写病历）**不经过控制面**：JWT 用共享密钥本地验签，授权与权益在签发时写入令牌与本 Cell 缓存。

## 5. 组件设计

### 5.1 控制面

| 组件 | 职责 | 关键约束 |
| --- | --- | --- |
| Tenant Registry | 租户目录：`tenant_code`、`instance_code`、名称、版本套餐、cell 端点、数据库主机、状态、配额、license 绑定 | 只做元数据，**不存患者数据**；写操作全部审计 |
| Provisioning | 开通流水线：建库 → 跑迁移 → 建 namespace/配额/网络策略 → 发 license → 建首个租户管理员 | 幂等、可重入；失败可回滚到"未开通" |
| auth（身份） | 用户/角色/登录/令牌；令牌增加 `tenant` 与 `instance` 声明 | 用户属于唯一租户；跨租户令牌在网关被拒 |
| license（§279） | 授权书按 `instance_code` 绑定 | 与本决策天然一致，无需改模型 |
| release（§273） | 版本与补丁；按 cell 批次发布 | 批次即 blast radius 控制 |
| 监控聚合 | 只读聚合各 cell 的运行指标（不含临床数据） | 控制面故障不影响 cell |

### 5.2 Cell（每院）

- **数据库**：独立 PostgreSQL 实例（独立账号、独立备份桶、独立 PITR 窗口）；服务连接串由 cell 注入，物理上无法连到别院。
- **计算**：独立 namespace；每服务 `Deployment` + `PDB` + `ResourceQuota` + `LimitRange`；`NetworkPolicy` 只允许本 namespace 内互访与出网白名单。
- **入口**：独立 ingress 与证书（`hospital-a.example`）；网关实例随 cell 部署，只认本 cell 的服务发现。
- **缓存/队列**：随 cell 独立（当前系统未依赖 Redis，未来引入时按 cell 隔离，禁止全平台共享队列）。
- **对象存储**：每院独立 bucket 前缀 + 独立 KMS key（影像、附件、备份）。
- **观测**：每 cell 独立 Prometheus 抓取目标与日志流，统一加 `tenant` 标签；告警按院路由到该院值班组。

### 5.3 路由与令牌

1. DNS/ingress 以 `hospital-a.example` 指向 Cell A 的网关；
2. 网关注入 `X-Tenant`（来自 Host 映射或令牌 `tenant` 声明，二者必须一致，否则 403）；
3. 令牌由控制面 auth 签发，含 `tenant`、`instance`；网关本地验签，不回调控制面；
4. 跨 cell 使用令牌：签发时绑定 `instance`，gateway 比对不一致即拒绝（防"拿 A 院令牌打 B 院入口"）。

### 5.4 数据层

- 每 cell 一个业务库实例，schema 结构与当前完全一致（`clinical_svc`、`pharmacy_svc`…）；
- Flyway 按 cell 独立执行同一套迁移，版本号一致，避免"50 个版本"；
- 迁移编排器记录 `(tenant, version, applied_at, checksum)`，可查"哪家跑到了哪版"；
- **不引入 `tenant_id` 列**：物理隔离后它只会增加误用面；跨院查询在架构上不存在。

## 6. 为什么不是其他方案（决策依据）

| 方案 | 否决理由 |
| --- | --- |
| 共享库 + `tenant_id` + RLS | 一次漏写 where / 一次错误连接池复用就串院；慢 SQL 与错误发布仍全局扩散；与"最高隔离"目标冲突 |
| 共享库 + schema-per-tenant | 数据边界尚可，但计算/连接池/发布仍共享，爆炸半径没有收敛；且大库运维（备份/恢复/升级）互相影响 |
| 一院一整套物理机（传统私有化） | 隔离足够，但版本碎片化、升级不可控、无法统一观测与安全补丁，长期不可维护 |
| **本决策：cell（独立数据面 + 共享控制面）** | 隔离强度接近私有化，运维与版本仍统一；控制面不参与读路径，故障不扩散 |

## 8. 与现有系统的迁移

- 当前单实例（`MEDASSIST-DEV-0001`）注册为 `tenant-001`，不迁移数据、不改表结构；
- 现有 `campus` 保持为院内多院区；
- 现有 license 的 `instance_code` 直接复用为租户实例键；
- 新增客户一律走"新建 cell"，不再往现有库里加医院。

## 9. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 控制面故障导致无法登录/开通 | 读路径不依赖控制面；控制面多副本 + 只读降级；登录令牌 TTL 内继续可用 |
| 每 cell 资源成本高 | 按院规模设两档 cell 规格（标准/大型）；闲置 cell 可缩容到最小副本 |
| 版本碎片化 | 单一镜像 + 按 cell 批次灰度；迁移版本强一致；禁止 per-tenant 代码分支 |
| 租户管理员越权 | 角色模型加 `tenant` 作用域；所有管理接口校验 `X-Tenant` 与目标对象一致 |
| 备份/恢复误操作 | 每 cell 独立备份账号与桶；恢复演练在隔离网络进行；跨 cell 恢复在工具层禁止 |

## 10. 待办决策（后续按需）

- 集团客户未来若要求跨院汇总：需单独立项（去标识汇总仓 + 出域审批），不在本 ADR 范围；
- 是否引入 Redis：若引入，必须按 cell 独立部署，禁止全平台共享实例；
- 单院多活（同城双活）：按三甲合同单独设计，不在本期。
